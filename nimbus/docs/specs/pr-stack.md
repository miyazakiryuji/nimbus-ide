# 積み上げた PR

**タスク**: T-135 / **実装**: `extensions/nimbus/src/core/prStack.ts`（判定）,
`extensions/nimbus/src/prStack.ts`（VS Code 層） / **テスト**: `src/test/prStack.test.ts`

## なぜ

1 つの大きな PR を分けて積むと、レビューは通しやすくなる代わりに**運用が難しくなる**。

- 積んだ順を間違えると入らない
- 下が入った瞬間、上の PR の差分が**別物に見える**（まだ入っていない下の変更まで自分の差分に混ざる）
- 下が入った後の**付け替え**を忘れると、入ったはずの変更が上の PR に残り続ける

3 つとも「知っていれば防げる」類で、知っていても忘れる。だから機械が出す。

## 出るもの

| コマンド | すること |
| --- | --- |
| `nimbus.showPrStack`（積み上げた PR を見る） | 積み方を木で出し、**入れる順**を添える |
| `nimbus.restackAfterMerge`（下が入った PR を向け直す） | 入ったブランチを選ぶと、上の PR の付け替え手順を出す |

取得は `gh pr list --json number,title,headRefName,baseRefName,isDraft`。
幹の名前は `origin/HEAD` から取り、無ければ `main`。

## 組み方

幹を向いている PR が根。その PR のブランチを向いている PR が、その上。

```
main
├─ #12 土台を足す
  └─ #13 API を足す
    └─ #14 画面を足す（下書き）
└─ #15 別件

入れる順: #12 → #13 → #14 → #15
```

**輪になっていたら組み込まない。** 壊れた状態を「積んである」と見せると、
入れる順を信じて操作してしまう。`orphans` で「どこにも繋がらなかった PR」として別に出し、
理由の候補（下の PR が閉じている／幹の名前が違う）を添える。

## 付け替え

いちばん忘れる作業。`afterMerge` が、入ったブランチを base にしている PR を拾い、
その base を**入った PR の base**（＝ふつうは幹）へ向け直す手順を出す。

```bash
git switch feat/api
git rebase --onto origin/main origin/feat/base
git push --force-with-lease origin feat/api
gh pr edit 13 --base main
```

`--onto` を使うのは、素の `git rebase` だと**既に入っているコミットが重複して当たる**ため。
`--force-with-lease` を使うのは、他の人が同じブランチを進めていたときに気づくため。

## こちらからは操作しない

出すのはコマンドの中身まで。PR の base を書き換えるのは、**他人のレビューが載っている場所への変更**なので、
走らせるのは人。`shellscript` の未保存エディタに出して、読んでから実行してもらう。

## 確認項目

- [ ] 3 段積んだ PR が木になり、入れる順が下から出る
- [ ] 幹を向いた別件の PR が、積みとは別の根として並ぶ
- [ ] 下書きの PR に「（下書き）」が付く
- [ ] base が互いを指す壊れた PR が「迷子」に出て、木には出ない
- [ ] 入ったブランチを選ぶと、その上の PR **だけ**の付け替えが出る（2 段上は出ない）
- [ ] `gh` が無い環境で、エラーではなく案内が出る
