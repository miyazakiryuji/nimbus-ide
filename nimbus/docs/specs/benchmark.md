# 改善前後のベンチ比較

「速くなった気がする」を数字で確定させる（`tasks.md` T-130）。

## 何を解決するのか

性能の改善は、**やった本人がいちばん「速くなった」と思い込みやすい**。
数字を出せば解決、でもない — **1 回ずつ測って 3% 速くなったと言うのは、測っていないのとほぼ同じ**。
計測はばらつくので、そのばらつきを超えていなければ、差があるとは言えない。

証跡つき完了報告（[completion-evidence](completion-evidence.md)）と同じ考えかたで、
**言い切れないときは言い切らない**。ここを緩めると、この機能は
「**改善したことにする道具**」になり、無いほうがましになる。

## 振る舞い

`Nimbus: 改善前後のベンチを比べる`。改善前・改善後の計測結果を貼ると、比較を開く。

読むのは `名前: 12.3 ms` の形の行。`名前 = 1500 ops/sec` や `名前  98 ms` も読む。
**読めない行は黙って飛ばす** — 無理に数字を拾うと、件数やバージョン番号を計測値として比べてしまう。

### 判定

| 出しかた | 条件 |
| --- | --- |
| 速くなった／遅くなった | 差が**ばらつきの 2 倍**を超え、かつ 1% 以上 |
| 判断できない | それ以外。**1 回ずつしか測っていない場合は必ずこちら** |

ばらつきは**中央絶対偏差**（中央値からの差の中央値）で見る。平均と標準偏差ではなく
中央値を使うのは、計測には外れ値が普通に混じるため（他のプロセスが動いた、など）。

単位が `ops/sec` `fps` `MB/s` などなら「大きいほど良い」、それ以外は「小さいほど良い」。
時間が大半なので、知らない単位は「小さいほど良い」に倒す。

**言い切れないものにも数字は出す**が、「**改善したことにしないでください**」と添え、
「回数を増やして測り直す」ことを勧める。

## 設計

- `extensions/nimbus/src/core/benchmark.ts` — 読み取りと判定（VS Code 非依存・単体テスト 12 件）
- `extensions/nimbus/src/benchmark.ts` — 貼ってもらう画面

同じ名前どうしだけを突き合わせる。片側にしか無い項目は比べない（別のものを比べても意味が無い）。
並びは**言い切れるものが先**、その中では効果の大きい順。

## 受け入れ条件

- [x] 中央値と散らばりが外れ値に引きずられない
- [x] 単位から「大きいほど良い」かを決める
- [x] 計測らしい行だけを読む（件数やバージョンを拾わない）
- [x] ばらつきを超えた差だけを「速くなった」と言う
- [x] **1 回ずつしか測っていなければ必ず「判断できない」**
- [x] 遅くなったことも同じ厳しさで言う
- [x] 同じ名前どうしだけを突き合わせる
- [x] 報告に「改善したことにしないでください」を書く
- [ ] 実際のベンチでの確認（未実施）

## 決めなかったこと・やらないこと

- **統計的検定（t 検定など）** — 正規分布を仮定できないうえ、p 値を出すと
  「有意だから改善」と読まれる。**ばらつきの何倍か**という、読んで分かる基準に留めた
- **ベンチを走らせる** — 走らせかたはプロジェクトごとに違いすぎる。貼ってもらう形にした
- **自動で回数を増やす** — 時間がかかるものを黙って何度も走らせない。勧めるだけ
