# コンフリクトの解決を手伝う

競合を読み解いて、両方の意図を残す解決を助ける（`tasks.md` T-115）。

## 何を解決するのか

競合の解決がつらいのは、`<<<<<<<` の左右を**目で見比べて意図を当てる**ところにある。
機械で分かるのは「どこが競合しているか」「両側が何行か」までで、そこは機械に任せてよい。

**この開発では複数の AI が 1 つのブランチを触る。**だから競合の大半は
**追記どうしのぶつかり**になる — `tasks.md` に別々の行を足した、`package.json` の
`contributes` に別々のコマンドを足した、など。その形はたいてい「両方残す」が正解なので、
その選択肢を一等地に置く。

## 振る舞い

`Nimbus: コンフリクトの解決を手伝う`。

1. `git diff --name-only --diff-filter=U` で競合中のファイルを集める
2. ファイルを選ぶ（1 件ならそのまま）→ エディタで開く
3. 「1 件ずつ選んで解決する」か「Claude に相談する」を選ぶ
4. 1 件ずつ **こちら / むこう / 両方残す / そのままにする** を選ぶ
5. 選んだとおりに書き戻す（保存は人がする）

**追記どうしに見える競合では「両方残す」を先頭に出す。**判定は
「両側に中身があり、共通の行が無い」という目安で、**これを根拠に自動では決めない**。

### 消さないための約束

- **選ばれなかった競合はマーカーごと残す。** 黙って片方を採ると変更が消える
- **途中でやめたら何も書き換えない**
- **マーカーが閉じていないファイルは解釈しない。** 中途半端に解釈して書き戻すと、
  残っていた変更まで消える。読み取れないときはその旨だけ伝える
- 書き戻すのはエディタのバッファまで。**保存と `git add` は人の手に残す**

### Claude に相談する

両側（と、`diff3` 形式なら分岐元）をそのまま貼った相談文をコックピットへ送る。
「**両方の変更の意図を汲んだ解決案**を出してください。片方を捨てる場合は理由も」と頼む。
意図の読み取りは機械の仕事ではないので、ここは Claude に渡す。

## 設計

- `extensions/nimbus/src/core/conflicts.ts` — マーカーの読み取りと書き戻し（VS Code 非依存・単体テスト 14 件）
- `extensions/nimbus/src/conflicts.ts` — git の実行と選ばせるところ

`merge.conflictStyle=diff3` の分岐元（`|||||||`）にも対応し、「分岐元に戻す」も選べる。

## 受け入れ条件

- [x] 両側の中身とラベルを読む
- [x] `diff3` 形式では分岐元も読む
- [x] こちら / むこう / 両方 / 分岐元 のとおりに書き戻す
- [x] 選ばなかった競合はマーカーごと残る
- [x] 閉じていないマーカーは解釈しない（元のまま返す）
- [x] 複数の競合をそれぞれ別に解決できる
- [x] 追記どうしの目安（共通行が無い）を判定する
- [ ] 実際の競合での画面確認（未実施・競合を作る必要があるため）

## 決めなかったこと・やらないこと

- **自動でマージする** — 目安は出すが、決めるのは人。並行開発で「よかれと思って片方を捨てる」
  のが一番損害が大きい
- **3-way マージの再実行** — git がすでにやったことをやり直さない。ここが扱うのは
  git が「人に決めさせる」と判断した部分だけ
- **VS Code 標準のマージエディタの置き換え** — 標準の差分表示はそのまま使える。
  ここが足すのは「一括で両方残す」と「Claude に相談する」の 2 つの導線
