# 証跡つき完了報告

## 何を解決するのか

「できました」は、それ自体では何の情報も持たない。テストを走らせたのか、通ったのか、
何を変えたのか — どれも分からないまま「完了」だけが届く。**「動いた気がする」を排除する。**

対応する tasks.md の項目: T-081。

## 振る舞い

### 「テストの証跡」（「セッションの中身」ビュー）

セッション中に走った**テストコマンドだけ**を拾い、成否とともに並べる。
行を選ぶと出力が tooltip に出る。

| 表示 | 意味 |
| --- | --- |
| ✅ 成功 | 失敗 0 件と読める出力が返った |
| ❌ 失敗 | 失敗 1 件以上、またはツール自体がエラー |
| ⚠️ 判定できず | 出力から成否を読み取れなかった |

### 完了報告（`nimbus.completionReport`）

コマンド **「Nimbus: 完了報告を作る（証跡つき）」**。Markdown を 1 枚開く。

1. **判定** — 「テストで裏づけられています」か「まだ『完了』とは言えません」
2. **変えたもの** — 指示ごとに、その指示から生まれた書き込みと読んだファイル（T-024 を再利用）
3. **テストの実行** — コマンドごとに成否と出力（800 文字で畳む）

テストが通っていないときは、報告を開いたうえで**警告も出す**。

### 判定できるコマンド

`npm` / `pnpm` / `yarn` / `bun` の `test`、`node --test`、`pytest`、`jest`、`vitest`、
`mocha`、`ava`、`rspec`、`phpunit`、`ctest`、`go test`、`cargo test`、`flutter test`、
`dart test`、`gradlew *test*`、`mvn *test*`、`swift test`、`dotnet test`、
`bash *test*.sh`（`nimbus/scripts/test.sh` を含む）。

## 設計

- `extensions/nimbus/src/core/evidence.ts` — 判定のすべて。VS Code 非依存
- `extensions/nimbus/src/completionReport.ts` — 報告の組み立てと表示
- `extensions/nimbus/src/activityView.ts` — 「テストの証跡」グループ

### 効かせた 2 つの判断

**1. 判定できない出力を「通った」に倒さない。**
出力の形はランナーごとに違う。読めなかったものを成功にすると、**報告そのものが嘘になる**。
`unknown` という段を用意して、分からないことを分からないと言う。

**2. 失敗を成功より先に見る。**
失敗時の出力にも成功件数が並ぶ（`# tests 226 / # pass 225 / # fail 1`）。
成功の言い回しを先に当てると、この出力を「成功」と読んでしまう。
失敗の判定は 1 件以上（`[1-9]`）を求めるので、`# fail 0` と食い違うことはない。

## 受け入れ条件

- [x] 主要なランナーのテストコマンドを拾い、`npm run compile` などは拾わない（単体テスト）
- [x] 判定できない出力を「通った」に倒さない（単体テスト）
- [x] `# pass 225 / # fail 1` を失敗と判定する（単体テスト）
- [x] ツール自体のエラーを失敗として扱う（単体テスト）
- [x] 結果がまだ返っていない実行も、走らせた事実として残す（単体テスト）
- [x] 直して通し直した場合は、最後の実行で判断する（単体テスト）
- [ ] 画面確認: 完了報告を開き、テスト未実行のときに警告が出る

## 決めなかったこと・やらないこと

- **完了を機械的にブロックはしない。** 判定して見せるところまで。
  テストが無いリポジトリもあり、そこで作業を止めるのは邪魔にしかならない
- **タスク（カンバン）の完了と連動させていない。** カンバンのタスクは別セッションで走り、
  その記録は拡張側の `retained`（アクティブなセッションぶんだけ）に入らない。
  連動させるにはセッションごとのイベント保持が要る（T-039 と一緒に扱うのが自然）
- **カバレッジは見ていない。** 「テストが通ったか」と「十分か」は別の問いで、
  後者は T-109（カバレッジ差分）の担当
