# レビュー済み／未レビューの管理

大きな変更を分割して見るときに、「どこまで見たか」を覚えておく（`tasks.md` T-160）。

## 何を解決するのか

変更が数十ファイルに及ぶと、人は途中で中断する。中断したときに「どこまで見たか」が
残っていないと最初から見直すことになり、**それが嫌でレビュー自体が雑になる**。

エージェントに書かせるほど 1 回の変更は大きくなるので、この問題は Nimbus では
避けて通れない。仕組みは小さくてよく、確実であることのほうが大事。

## 振る舞い

サイドバーの「レビュー」。見出しに `3/12 済み` のように進み具合が出る。

- 行をクリックすると**差分が開く**（印だけの画面にしない）
- 行の ✓ で「レビュー済み」、○ で「未レビュー」に戻す
- 見出しの「変更の一覧を取り直す」で `git diff HEAD` を読み直す
- 見出しの「レビューの印をすべて外す」で最初からやり直す

並びは **見たあとに変わったもの → 未レビュー → 済み**。先に見るべきものが上に来る。

### 見たあとに変わったものは、見たままにしない

**印はパスではなく「そのとき見た中身の指紋」に対して付ける。**
見たあとにそのファイルが書き換わると、レビュー済みは自動で外れ、
「見たあとに変わった」と理由が出る。

これがこの機能の芯にあたる。パスに印を付けるだけの作りにすると、
**確認したつもりの見落とし**を作る道具になってしまう。エージェントは
レビュー中にも別のファイルを書き換えるので、この事故は普通に起きる。

指紋は簡単なハッシュで足りる。衝突しても「見たはずのものをもう一度見る」だけで、
実害が無い側に倒れる。

### 印の後始末

コミットして変更が無くなったファイルの印は捨てる。溜め込むと、
同じパスを次に触ったときに「見たことがある」と誤解する。

## 設計

- `extensions/nimbus/src/core/reviewState.ts` — 指紋・突き合わせ・並び（VS Code 非依存・単体テスト 10 件）
- `extensions/nimbus/src/reviewView.ts` — `git diff HEAD` の読み取りとツリー

印の保存は `workspaceState`（リポジトリごとに別で、他のプロジェクトに漏れない）。
未追跡ファイルは中身を読まず「新規ファイル: <パス>」を指紋の材料にする —
中身まで読むと巨大ファイルで詰まるうえ、新規は「見たかどうか」だけで足りるため。

## 受け入れ条件

- [x] 印が無いファイルは未レビュー
- [x] 見たときの指紋と一致すればレビュー済み
- [x] **見たあとに中身が変わったらレビュー済みが外れる**
- [x] 並びは 見たあとに変わった → 未レビュー → 済み
- [x] 印を付け直すと、そのときの中身で覚え直す
- [x] 変更が無くなったファイルの印は捨てる
- [x] ビューとコマンドが出る（GUI テスト `18-review.mjs`）
- [ ] 実際に変更のあるリポジトリでの通し確認（未実施）

## 決めなかったこと・やらないこと

- **hunk 単位のレビュー印** — ファイル単位で足りる。hunk 単位にすると印の管理が
  レビューより手間になり、本末転倒になる
- **チームでの共有** — 印は自分の手元だけ。誰がどこまで見たかの共有は
  T-211（レビュー依頼の導線）の領分
- **自動でレビュー済みにする** — 「開いたら済み」にはしない。開いただけで見たことに
  するのは、この機能が防ぎたかったことそのもの
