# セッションの中身（サブエージェント・フック・触ったファイル・コンパクション）と通知

## 何を解決するのか

セッションの中では、画面に出ていないことが大量に起きている。サブエージェントは独立した文脈で
動いて親には最終サマリーしか返さないし、フックは黙って発火して黙ってブロックするし、
コンパクションは何の前触れもなく履歴を畳む。**「なんでこうなったの？」に答える材料が無い**のが問題。

対応する tasks.md の項目: T-018（サブエージェントのツリー可視化）/ T-019（完了通知）/
T-022（コンパクションの可視化）/ T-023（読み込まれたファイル一覧）/ T-027（フック発火ログのビューア）。
Inbox の T-015（デバッグモード）が求めていた面もここでほぼ埋まる。

## 調べたこと — 材料は既に届いていた

`session/normalize.ts` は SDK メッセージのうち `system/init`・`assistant`・`user`・`result` だけを
拾い、残りを捨てていた。SDK 0.3.226 が実際に投げているものを数えると **38 種類**あり、
このうち次を拾えば上の 4 つはすべて作れる。

| SDK メッセージ | 使い道 |
| --- | --- |
| `hook_started` / `hook_progress` / `hook_response` | フックの発火ログ（T-027）。`outcome` / `exit_code` / `stderr` 付き |
| `task_started` / `task_progress` / `task_updated` | サブエージェント（T-018）。指示・種別・使用トークン・ツール回数・状態 |
| `compact_boundary` | コンパクション（T-022）。`trigger`（manual / auto）と前後のトークン数 |

触ったファイル（T-023）は既存の `tool-use` イベントから組み立てられる（新しい購読は要らない）。

## 振る舞い

### 「セッションの中身」ビュー

サイドバー Nimbus の **「セッションの中身」**（既定は折りたたみ）。4 つのグループを持つ。
**別々のビューを 4 つ足さない** — サイドバーが破綻するうえ、どれも「いま何が起きたか」を
追うための情報なので、同じ面にあるほうが読める。

1. **サブエージェント**（T-018）— 開始が新しい順。行に「説明 / 種別 · 状態」。展開すると
   指示・最後のツール・消費（トークン / ツール回数 / 所要）・まとめ・エラー
2. **フック**（T-027）— 発火が新しい順。行に「フック名 / イベント名 · 結果 · 時刻」。
   展開すると出力・stderr・終了コード。**失敗したものはアイコンで一目で分かる**
3. **触ったファイル**（T-023）— 最後に触ったのが新しい順。読み／書きを分けて数える。
   **行をクリックするとエディタで開く**（一覧から辿れないと見えているだけで終わる）
4. **コンパクション**（T-022）— 発生が新しい順。「自動 · 100,000 → 25,000（75% 削減）」

### 手動コンパクション（T-022）

コマンド **「Nimbus: 文脈を圧縮する（コンパクション）」**（`nimbus.compact`）。
SDK に専用の API は無く、CLI と同じく `/compact` を送るのが正規の経路。
実行すると `compact_boundary` が返り、上のビューに記録が残る。

### OS 通知（T-019）

- **ターンが終わったとき**と**承認待ちが増えたとき**に OS の通知を出す
- 既定では **ウィンドウが前面に無いときだけ**。見ている画面に重ねて出しても邪魔なだけで、
  それを繰り返すと通知そのものを切られる（T-087 の集中モードと衝突しない形）
- 設定 `nimbus.notifications.enabled` / `nimbus.notifications.onlyWhenUnfocused`
- macOS は `osascript`、Linux は `notify-send`。**Windows はウィンドウ内通知に落とす**
  （PowerShell はスクリプト文字列への埋め込みを避けられず、壊れる余地が残るため）

## 設計

- `extensions/nimbus/src/events.ts` — `hook` / `subagent` / `compaction` の 3 種を追加（既存は変更なし）
- `extensions/nimbus/src/session/normalize.ts` — `system` の分岐を subtype ごとの switch に。
  SDK の 3 段階（started / progress / response）は **1 種類のイベントに畳んで**渡す
  （見たいのは「どのフックが何を返したか」であって SDK の内部段階ではない）
- `extensions/nimbus/src/core/activity.ts` — イベント列を畳んで一覧にする。VS Code 非依存
- `extensions/nimbus/src/activityView.ts` — ツリー表示。状態は持たない
- `extensions/nimbus/src/core/notify.ts` — 通知コマンドの**組み立てだけ**。起動はしない
- `extensions/nimbus/src/extension.ts` — ビュー登録・通知の呼び出し・`nimbus.compact`

### 通知でシェルを使わない理由

タスク名やエラー文をシェル文字列に埋め込むと、`"` が 1 つ入るだけで壊れる。最悪、
`$(...)` が実行される。そのため `buildNotifyCommand` は **コマンドと argv を返すだけ**にし、
`spawn`（シェル無し）で起動する。macOS は `osascript -e 'on run argv' … -- 本文 タイトル` の形で、
本文をスクリプト文字列に一切埋め込まない。

- [x] フックの失敗（outcome / exit_code / stderr）が残る（単体テスト）

## 決めなかったこと・やらないこと

- **サブエージェントの会話そのものは出さない。** SDK が親に流すのは進捗とサマリーだけで、
  中の全メッセージは届かない（`skip_transcript` の扱いも含めて SDK 側の設計）。
  出せない情報を「出せるように見せる」ほうが害が大きい
- **フックの一覧は履歴を持たない。** 表示のもとは拡張が保持しているイベント列（上限 2000 件）で、
  セッションをまたぐと消える。永続化は T-034 の課題としてまとめて扱う
- **圧縮前に何を残すか選ばせる画面（T-154）はここに含めない。** 発生を記録することと、
  中身に介入することは別の仕事
- **Windows の OS 通知は見送った。** 埋め込みを避けられないため。必要になったら
  通知専用の小さなヘルパー実行ファイルを同梱する形で解く
