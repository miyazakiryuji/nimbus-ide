# ヘッドレス実行と MCP ツールの単体実行

対応するタスク: T-093（ヘッドレス Nimbus）・T-235（MCP ツールの単体実行）。

どちらも「**エージェントを介さずに確かめる**」ための道具。
片方は GUI を外し、もう片方はエージェントを外す。

---

## T-093 ヘッドレス Nimbus

`nimbus/scripts/headless.mjs`。GUI を立ち上げずに、画面と同じワークフローを CI から回す。

```
node nimbus/scripts/headless.mjs --list
node nimbus/scripts/headless.mjs -w "不具合を直す" -i "起動時に落ちる" --yes --require-tests
node nimbus/scripts/headless.mjs -w 1 -i "..." --dry-run
```

### 判断は画面と同じものを読む

`extensions/nimbus/out/core/*.js` を `require` して使う（`workflow` / `policyProfiles` /
`evidence` / `risk` / `secrets`）。**CLI 用に書き直さない** — 書き直すと
「手元では通るのに CI では違う」が必ず起きる。
`core/*` が VS Code に依存していないのは、もともとこのため。

ビルドされていなければ、その場で言って止まる（`npm --prefix extensions/nimbus run compile`）。

### CI 特有の決めごと

| こと | どうするか | なぜ |
| --- | --- | --- |
| 人の確認（`confirm: true`） | `--yes` を付けない限り**実行そのものを断る** | 黙って飛ばすと、確認を置いた意味が消える。飛ばすと分かって回してもらう |
| 危険なツール | その場で `deny` して落とす | 承認する人がいない。待たせると CI が固まる |
| 秘匿ファイルの読み取り | プロファイルに従って遮断 | 画面と同じ判断（`core/secrets.ts`） |
| 段をまたぐ文脈 | `resume` で同じセッションを続ける | 段ごとに忘れると、調査 → 実装が繋がらない |
| 上限 | `--max-turns`（既定 30） | 止まらない実行を CI に置かない |

既定のプロファイルは**「調べるだけ」**。CI から呼ぶものが既定で書き換えられるのは危ない。

### 終了コード

| 値 | いつ |
| --- | --- |
| 0 | 最後の段まで通った |
| 1 | 途中の段が失敗した／`--require-tests` を付けたのにテストが通った証拠が無い |
| 2 | 引数が違う・ビルドされていない・その他の異常 |

`--json <パス>` を付けると、出来事を 1 行 1 件（NDJSON）で書き出す。

### 受け入れ条件

- [x] `--list` が組み込みワークフローと各段を出す
- [x] `--dry-run` が API を呼ばずに、送る文をそのまま出す
- [x] 確認のある段があるのに `--yes` が無ければ、実行せず終了コード 2
- [x] 知らないワークフロー名／番号で終了コード 2
- [x] `--json` が NDJSON を書く
- [ ] 実際に API を呼ぶ経路（`--yes` あり）を一度手で回す

## T-235 MCP ツールの単体実行

コマンド **「Nimbus: MCP ツールを 1 回だけ試す」**（`nimbus.runMcpTool`）。

エージェントに頼まず、ツールを直接 1 回呼ぶ。
これが無いと、ツールが期待どおり返らないときに
**エージェントが呼び方を間違えたのか、ツールが壊れているのか**が切り分けられない。

### 繋ぎかた

Nimbus 自身のツール（`nimbus_lsp` / `nimbus_debug`）は**拡張ホストのプロセス内**にいる。
`InMemoryTransport.createLinkedPair()` で `Client` を直接繋ぐので、
**別プロセスも API 呼び出しも課金も発生しない**。

セッションへ渡すのと**同じ実体**を使う（`inProcessMcpServers()` は
`lspMcpServer()` / `debugMcpServer()` を呼ぶ。どちらもキャッシュされた同一インスタンス）。
別に作ると「単体では通るのにセッションでは違う」が起きる。

繋いだ `Client` は `finally` で必ず閉じる。

### 引数の聞きかた（`core/mcpArgs.ts`）

ツールの `inputSchema`（JSON Schema）から聞くべき項目を作る。

- **必須を先に出す** — 任意から聞くと、必須に辿り着く前に諦められる
- `enum` があれば入力欄ではなく選択にする
- `default` は入力欄に入れておく
- 型に合わせて変換する（`"3"` ではなく `3` を渡す）。
  **文字列のまま渡すとサーバー側が型で弾き、「動かない」としか分からない**
- 空のまま飛ばした任意項目は**キーごと入れない**（`undefined` を渡すのと振る舞いが変わるサーバーがある）
- 途中で閉じたら実行しない（空で呼ぶと事故になる）

結果は Markdown で開く。**渡した引数もそのまま載せる** — 引数が見えないと再現できない。
失敗も同じ経路で見せる（「何も出ない」が一番困る）。
`content` を持たない古い形（`toolResult`）も受ける。

### 受け入れ条件

- [x] スキーマ → 項目 → 引数 → 実行 → 表示 を、実物の MCP サーバーで通した
      （`createSdkMcpServer` で作ったサーバーへ `InMemoryTransport` で繋ぎ、
      `listTools` の返す JSON Schema をそのまま `toFields` に通して確認）
- [x] 必須が空なら理由を言って止める
- [x] 型が違えば、呼ぶ前に言う
- [x] 成功・失敗・空、どれも同じ形で見せる
- [ ] 画面確認: コマンドパレットから呼び、`nimbus_lsp` のツールを 1 つ実行する
