# 落ちた CI を調べる（T-131）

赤くなってから人がログを開くまでの間が、いちばん無駄な時間。
ログは GitHub にあり、`gh` で取れる。**取りに行って、原因の当たりをつけるところまで**を先にやる。

## 振る舞い

コマンド **「落ちた CI を調べる」**（`nimbus.investigateCi`）:

1. `gh` があるかを確かめる（無ければ入れ方を伝えて終わる）
2. `gh run list` で直近 10 件を取り、**落ちているもの**を既定に選ぶ
3. どの実行を見るかは選べる（直近が本命とは限らない）
4. `gh run view <id> --log-failed` で**失敗したステップのログだけ**を取る
5. 「原因を調べさせる」でコックピットへ投入

## 実装

- `extensions/nimbus/src/core/ciFailure.ts` — `gh` の出力の読み取りと文面（純関数）
- `extensions/nimbus/src/ciFailure.ts` — `gh` の実行
- テスト: `extensions/nimbus/src/test/ciFailure.test.ts`

## 決めたこと

**認証を自前で持たない。** `gh` に任せる。トークンを Nimbus が預かると、
保管と失効の面倒を全部引き受けることになる。`gh` が無ければ、その旨だけを伝える。

**走っている最中の実行を「失敗」と見ない。** `status === 'completed'` かつ
`conclusion` が `failure` / `timed_out` のものだけ。

**ログは末尾から切る。** 落ちた理由は終わりにある
（[terminal-capture](terminal-capture.md) と同じ整形を使う）。

**まだ直させない。** CI のログは環境の違いを含む。まず
「何が失敗したのか」と「**手元で再現するのか、CI 固有なのか**」を答えさせてから、方針を書かせる。
ここを飛ばすと、CI でしか起きない問題に手元の修正を当ててしまう。

**ログが取れなくても投入できる。** どの実行が落ちたかだけでも手がかりになる。

## 確認すること

- [ ] `gh` が無い環境で、入れ方を伝えて終わる
- [ ] 落ちた実行があると、それが既定で選ばれる
- [ ] 走っている最中の実行は「落ちている」と扱われない
- [ ] 失敗ログの末尾が投入される（長いときは「先頭 N 行は省略」）
- [ ] 落ちている CI が無ければ、その旨が出る

## 残っていること

- GitHub Actions だけ（GitLab CI / CircleCI は見ていない）
- 赤くなった**瞬間**には気づかない（コマンドを叩いたときに取りに行く）。
  常時監視は API の消費とレート制限を考えてから
