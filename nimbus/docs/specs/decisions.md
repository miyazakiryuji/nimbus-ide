# 決めたことを残す（ADR）（T-060）

設計の判断は**会話の中で決まって、会話と一緒に消える**。半年後に
「なぜこうなっているのか」を誰も説明できないのは、この取りこぼしが原因。

Nimbus がやるのは**置き場所と型を用意すること**と、**会話から候補を拾うこと**。
文章にするのはセッション側で、**「なぜそう決めたか」を書かせる**のが要点。

## 振る舞い

コマンド **「決めたことを残す（ADR）」**（`nimbus.writeAdr`）:

1. 何についての判断かを 1 行入れる
2. `nimbus/docs/decisions/NNNN-<title>.md` を作って開く
3. 会話から拾った「決めたことらしい発言」が候補として入っている
4. **「理由を埋めさせる」**を押すと、`なぜ` と `選ばなかった案` を埋める指示が送られる

下書きには**空欄をそのまま残す**。埋まっていない方が、埋まったふりをしているより正しい。

## 実装

- `extensions/nimbus/src/core/decisions.ts` — 候補の抽出・採番・ADR の本文（純関数）
- `extensions/nimbus/src/decisions.ts` — ファイル作成と会話の受け取り
- テスト: `extensions/nimbus/src/test/decisions.test.ts`

## 決めたこと

**置き場所は `nimbus/docs/decisions/`。** 仕様書（`specs/`）とは分ける —
仕様は「いまどうなっているか」、ADR は「いつ何をなぜ決めたか」で、寿命が違う。

**採番はファイル作成そのものに任せる（`wx`）。** 「最大番号を読む」と「書く」の間に
他のセッションが入る。この作業ツリーは複数セッションで共有されていて、実際に
この隙間で事故が起きた。既にあれば失敗する形で作り、失敗したら番号を取り直す。

**取りこぼしより誤検出の方が悪い。** 拾うのは「〜にする」「〜は見送る」「〜を採用する」の
ような判断らしい言い回しだけ。前置き（「まず」「次に」）から始まる文と、
短すぎる／長すぎる文は落とす。**拾えたものにも「誤検出があります」と添える。**

**「なぜ」を必ず書かせる。** 理由の無い記録は、次に読む人を縛るだけで、
判断し直すこともできない。「選ばなかった案」も同じ理由で欄を置く。

## 確認すること

- [ ] コマンドで `nimbus/docs/decisions/0001-….md` ができて開く
- [ ] 会話で「〜にします」と言った内容が候補として入る
- [ ] 状況説明（「この関数は 3 箇所から呼ばれています」）は入らない
- [ ] 2 回作ると番号が 0002 に進む
- [ ] **同時に 2 つ作っても同じ番号にならない**（別セッションと同時に実行して確認）
- [ ] 「理由を埋めさせる」でコックピットに指示が送られる

## 残っていること

- 候補の抽出は日本語の言い回しのみ（英語の会話では拾えない）
- 既存の ADR を更新する導線は無い（新規作成だけ）
- 仕様書（`specs/`）への反映は手作業。[T-003 の仕様書き起こし](../../../tasks.md)と繋げる余地がある
