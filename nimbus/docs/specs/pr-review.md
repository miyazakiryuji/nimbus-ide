# PR レビューの取り込み

レビュー指摘を `file:line` つきでセッションに渡し、返信も下書きする（`tasks.md` T-116）。

## 何を解決するのか

レビューを直す作業がつらいのは、**指摘とコードの間を往復する**ところ。
ブラウザで指摘を読み、エディタで場所を探し、直し、またブラウザに戻って返信する。

`gh` は指摘を取ってこられるが、**`file:line` とコードの中身は繋いでくれない**。
ここが引き受けるのはその接続で、直すこと自体は Claude の仕事。

## 振る舞い

`Nimbus: PR のレビュー指摘を取り込む`。

1. いまのブランチの PR を `gh pr view` で調べる（無ければ番号を聞く）
2. `gh api repos/{owner}/{repo}/pulls/{n}/comments --paginate` で指摘を取る
3. **まだ対応していないもの**だけに絞る（解決済みと、スレッドの 2 件目以降＝返信を外す）
4. 「すべて直してもらう」か、1 件を選んで「返信の下書き」

ファイルごとにまとめ、行の順に並べる。**ファイル指定なし（PR 全体へのコメント）は必ず最後。**
直せる場所がはっきりしているものから片付けるほうが手が動く。

### 指摘はそのまま渡す

**要約しない。**要約するとレビュアーの言葉のニュアンスが落ちる。
指摘がついた差分（`diff_hunk`）も一緒に渡す。

頼みかたには 2 つ条件を書く。

- **直す前に、指摘が今のコードに当てはまるか確かめる**（既に直っていることがある）
- **納得できない指摘は、直さずに理由を書く**。言われたとおりに直すことが目的ではない

### 返信は下書きまで

**送信しない。**返信は人が読んでから出す。下書きには「取り繕わないこと」を求める —
直していないのに直したように書く返信が、レビューでいちばん害になる。

## 設計

- `extensions/nimbus/src/core/prReview.ts` — JSON の正規化・絞り込み・頼みかた（VS Code 非依存・単体テスト 10 件）
- `extensions/nimbus/src/prReview.ts` — `gh` の実行と選ばせるところ

形が違うもの（本文が無い等）は落とす。中途半端に出すと指摘の数が合わなくなるため。
変更後の行が無い指摘（消えた行への指摘）は `original_line` で示す。

## 受け入れ条件

- [x] `gh` の JSON を読む（返信・解決済み・行の指定なしも保つ）
- [x] 変更後の行が無ければ元の行で示す
- [x] 形が違うものは落とす
- [x] 解決済みと返信を外して、未対応だけに絞る
- [x] ファイルごと・行順にまとめ、ファイル指定なしは最後
- [x] 指摘を要約せずそのまま渡す（差分つき）
- [x] 返信の下書きは「取り繕わない」ことを求める
- [x] `gh` が無いときに、何を入れればよいか言う
- [ ] 実際の PR での通し確認（未実施）

## 決めなかったこと・やらないこと

- **返信を自動で送る** — 下書きまで。相手のいるやり取りを機械に任せない
- **指摘を解決済みにする** — GitHub 側の状態は変えない。直したかどうかの判断は人のもの
- **要約して渡す** — レビュアーの言葉をそのまま渡す。要約はニュアンスを落とす
