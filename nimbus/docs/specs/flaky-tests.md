# 不安定なテストの検出

同じコードのまま結果が変わるテストを見つける（`tasks.md` T-133）。

## 何を解決するのか

落ちたり通ったりするテストは、**放っておくと全部のテストが信用されなくなる**。
「また例のやつでしょ」で赤を見過ごすようになった時点で、テストの意味が消える。

エージェントに書かせるとテストの本数が増える。増えるほど、この崩れかたは早く来る。

## 振る舞い

`Nimbus: 不安定なテストを探す`。

1. テストを走らせるコマンドを決める（`nimbus.tests.command`。空なら毎回聞く）
2. 回数を選ぶ（3 / 5 / 10 / 20。多いほど見つかるが、そのぶん待つ）
3. その回数だけ回し、**TAP の出力**を突き合わせる
4. 結果を一枚の Markdown で開く

進捗を出し、**途中で取りやめられる**。落ちても止めずに最後まで回す
（落ちること自体が知りたい情報なので）。

### 判定

**1 回でも結果が変われば flaky。**「n 回中 1 回だけ落ちた」も flaky で、
たまたま今回通ったことに意味は無い。ここを「だいたい通っている」と丸めた瞬間に、
この機能は無意味になる。

| 見出し | 中身 |
| --- | --- |
| 揺れているもの | 通ったり落ちたりした。落ちた回数が多い順（＝当たりやすい順） |
| 毎回落ちているもの | 揺れではなく、単に落ちている |
| 回によって現れないもの | 実行のたびに出たり出なかったりする |

3 つめは、テスト名が動的に作られている（時刻や乱数を含む）ことが多く、
**それ自体が直すべき兆候**なので分けて出す。

揺れが見つからなかったときは「**その回数で出なかっただけかもしれない**」と断る。
「無い」と言い切ると、回数不足を見落とす。

## 設計

- `extensions/nimbus/src/core/flaky.ts` — TAP の読み取りと突き合わせ（VS Code 非依存・単体テスト 9 件）
- `extensions/nimbus/src/flaky.ts` — 繰り返し実行と進捗

TAP を選んだのは `node --test` がそのまま出すため。`# Subtest:` の見出しや診断行は
結果ではないので拾わない。`# SKIP` / `# TODO` の印は名前から外す（同じテストとして数えるため）。

## 受け入れ条件

- [x] TAP から結果を読む（見出し・診断行を拾わない）
- [x] 1 回でも結果が変われば flaky
- [x] 毎回落ちるものは flaky と区別する
- [x] 並びは 揺れ → 毎回落ちる → 通る。揺れは当たりやすい順
- [x] 回によって現れないテストを別に見つける
- [x] 揺れが無いときも「出なかっただけかもしれない」と断る
- [x] 途中で取りやめられる
- [ ] 実際の flaky テストでの確認（未実施）

## 決めなかったこと・やらないこと

- **自動で再実行して緑にする** — それは flaky を隠す行為で、この機能の目的の逆
- **flaky を隔離（quarantine）する** — 隔離すると直されなくなる。見つけて名指しするまで
- **TAP 以外の形式** — jest / vitest の JSON など形式ごとに増やすと、読み取りの誤りが
  そのまま誤検出になる。まず TAP だけを確実に読む
