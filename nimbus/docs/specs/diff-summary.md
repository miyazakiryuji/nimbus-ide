# 変更の要約（差分の見取り図）

差分を読む前に「何がどう変わったか」を構造で出す（`tasks.md` T-157）。

## 何を解決するのか

エージェントに書かせると 1 回の変更が大きくなる。`+420 −180` とだけ言われても、
どこから読めばいいか分からない。かといって全部読むと、読むこと自体が仕事になる。

**「何を意図した変更か」は機械には分からない。**分かるのは構造 —
どの export が増えて、どれが消えて、どのファイルが実装でどれがテストか。
それを先に読めれば、差分そのものを読む速さが変わる。

## 振る舞い

`Nimbus: 変更の要約を見る`。`git diff HEAD` を読んで、新しいタブに要約を開く。

1. **外から見える変化（export）** を最初に出す。API が変わったかはここだけ見れば分かる
2. 役どころごとに **実装 → テスト → 設定 → コア → 仕様** の順で並べる
3. ファイルごとに `+N −M` と、増えた／消えた宣言

そのあと「意図の要約を Claude に頼む」を選べる。構造を下敷きにして渡すので、
Claude は差分を読み直さずに意図の側だけを書ける。

**要約には「意図までは機械には分からない」と必ず書く。**過信させないため。

### 間違ったことを言わないための約束

- **消えて足された宣言は「変更」として扱い、増減には出さない。**
  中身を直しただけの関数を「消した」と出すと、API が壊れたように読める
- **字下げのある行は宣言として採らない。** 関数の中の `const local = 1;` まで拾うと、
  要約が局所変数で埋まって見取り図の役に立たなくなる（実装して気づいた）
- **`+++` / `---` のヘッダを行数に数えない。** 数えると、1 行も変えていないファイルが
  `+1 −1` に見える
- 消した export があるときは「呼び出し元が残っていないかを先に見る」と添える

### 生成物は畳む（T-140）

`build_runner` を回すと `*.g.dart` と `*.freezed.dart` が何十ファイルも動く。
それが手書きと同じ重みで並ぶと、**読むべき数行が埋もれる**。生成物は「動いた」ことが
分かればよく、中身を読む必要はほとんど無い。

- 判定は **名前 → 置き場所 → 冒頭の印** の順。`*.g.dart` / `*.freezed.dart` / `*.pb.go` /
  `*_pb2.py` / ロックファイル / `node_modules` `Pods` `build` `__generated__` など
- 名前で決まらないときだけ、**足された行の冒頭 5 行**に `GENERATED CODE` / `@generated` /
  `DO NOT EDIT` が無いかを見る。全文を見ると、生成物の話をしているだけのファイルを拾う
- 生成物の export は「外から見える変化」に混ぜない（数十件あると手書きの分が埋もれる）

**畳むが、隠さない。**「生成物 12 ファイル（+840 −120）」と件数・行数を出し、名前も並べる。
誤判定はありえるし、生成物が**動いていないこと**に気づきたい場面もあるため。
合計の行数には生成物も含める（変更全体の大きさは正しく伝える）。

### 元を直したら作り直す（T-141）

`model.dart` の `@freezed` を触ったのに `model.g.dart` を作り直し忘れると、
**型エラーではなく「古い実装が静かに動く」**という、いちばん気づきにくい壊れかたをする。

- `Nimbus: 生成物を作り直す` — プロジェクトの形から生成コマンドを決めて、端末で走らせる
- 設定 `nimbus.generate.offerAfterSave`（**既定 `false`**）を有効にすると、
  生成物のある元ファイルを保存したときに聞く。断れば、そのセッション中は聞き直さない

| プロジェクト | コマンド | 見ているもの |
| --- | --- | --- |
| Dart / Flutter | `dart run build_runner build --delete-conflicting-outputs` | `pubspec.yaml` に `build_runner` |
| Node（Prisma） | `npx prisma generate` | `package.json` の依存 |
| Node（GraphQL） | `npx graphql-codegen` | 同上 |
| Node（その他） | `npm run generate` | `generate` スクリプトがあるとき |
| Go | `go generate ./...` | `go.mod` |

**見つからなければ何も出さない。**当てずっぽうのコマンドを走らせると、別のものを壊しかねない
（`build_runner` の無い Flutter プロジェクトで走らせる等）。

**黙って走らせない。**生成は時間がかかるうえ、途中の状態で走らせたくない場面もある。
端末は隠さずに開く — 生成はよく失敗するので、出力が見えないと詰まる。

## まだコミットが無いフォルダ（T-353）

`git init` 直後（unborn HEAD）は `git diff HEAD` が rc=128 で
`fatal: ambiguous argument 'HEAD'` を返す。**変更が 1 つも無い平常の状態**なのに、
以前はそれを種類で分けずエラー通知へ流していたので、生の英語が赤で出ていた
（敵対的試験 adv-09）。

- コミットの有無は `git rev-parse --verify --quiet HEAD` で見る（英文を出さず rc で分かる）
- まだコミットが無いときは、`HEAD` ではなく**空ツリー**（`4b825dc642cb6eb9a060e54bf8d69288fbee4904`）
  と比べる。作業ツリーが空なら空出力、`git add` 済みの変更があれば新規作成として出る
- 生の英語（`fatal` / `ambiguous`）を利用者へそのまま貼らない
- 同じ穴が `impact.ts` / `reviewProgress.ts` / `changeStats.ts` などにも `git diff HEAD` 直打ちで
  残っている（横展開は別タスク）

## 決めなかったこと・やらないこと

- **意図を機械で推測する** — できない。構造だけを出して、意図は Claude に渡す。
  推測を書くと、間違っていたときに差分より信用されてしまう
- **言語ごとの厳密な構文解析** — 正規表現で読める範囲に留める。読めないものは黙って
  諦めるほうが、中途半端に読んで嘘を書くより安全（T-098 の LSP に寄せる余地はある）
- **コミット済み履歴の要約** — T-062（リリースノートの下書き）の領分。
  こちらは**まだコミットしていない変更**を対象にする
