# 変更の影響範囲

「この変更、何を壊す？」を適用の前に見せる（`tasks.md` T-158）。

## 何を解決するのか

いちばん確実な材料は、**消した／名前を変えた export を、まだ誰が呼んでいるか**。

型チェックも同じことを教えてくれるが、**同じ言語の中でしか効かず、しかも直したあとにしか出ない**。
エージェントが 40 ファイルを書き換えたあとに 30 個のエラーが出るより、
「この export を消すと 12 箇所が困る」を先に見るほうが、判断の順序として正しい。

## 振る舞い

`Nimbus: 変更の影響範囲を見る`。

1. `git diff HEAD` から**消した export** を拾う（[diff-summary](diff-summary.md) の結果を使う）
2. ワークスペースのソースを読み、その名前を**語の切れ目で**探す
3. 参照の多い順に並べて、`パス:行 — その行` を並べた一枚を開く

**変更したファイル自身は数えない。**定義していた行を「影響」と呼んでも意味が無い。
呼び出し元が残っていない export は報告しない（雑音になる）。

### 言い切らない

参照の探索は**名前で当たりをつけるだけ**。厳密な解決は LSP（T-098）の仕事で、
ここは**LSP が立ち上がっていなくても効く**ことを優先している。そのため:

- コメントや文字列の中も拾う（**誤検出は許す**）
- 動的な呼び出し（文字列経由）は見えない（**取りこぼす**）

だから出力は「呼ばれている**かもしれません**」と書き、「確認の出発点」と断る。
見つからなかったときも「動的な呼び出しは見えません」と添える —
**「無い」と言い切ると、それを信じて見落とす**。

見落とすより出しすぎるほうを選んでいる。壊れる場所を見逃すのが一番困るため。

## 設計

- `extensions/nimbus/src/core/impact.ts` — 探索と整形（VS Code 非依存・単体テスト 10 件）
- `extensions/nimbus/src/impact.ts` — 差分の取得とワークスペース検索

生成物と依存（`node_modules` / `out` / `.build` / `dist`）は探索しない。
当たっても直す先ではないため。読むファイルは 3000 件を上限にする（巨大なリポジトリで固まらせない）。
探索中は進捗を出し、**取りやめられる**ようにする。

## 受け入れ条件

- [x] 語の切れ目で探す（`foo` が `foobar` に当たらない）
- [x] 変更したファイル自身は数えない
- [x] 呼び出し元が残っているものだけ報告する
- [x] 参照の多い順に並べる
- [x] 識別子として不正な名前を正規表現に流し込まない
- [x] 参照が多すぎるときは打ち切り、打ち切ったことを言う
- [x] 見つからなかったときも、見えない呼び出しがあることを断る
- [ ] 大きなリポジトリでの速度の確認（未実施）

## 決めなかったこと・やらないこと

- **LSP で厳密に解決する** — 正確にはなるが、解析サーバが立ち上がっていない場面でも
  効いてほしい。T-098 が安定したら、そちらを**優先して使い、無ければ名前で探す**形に
  寄せる余地がある
- **影響の大きさを点数にする** — 参照の数以上のことは言えない。点数にすると
  根拠の無い重みづけを信じさせてしまう
- **自動で呼び出し元を直す** — 直すのは Claude の仕事。ここは「どこを見るか」までにする
