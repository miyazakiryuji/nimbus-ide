# コミットの分けかたの提案

作業ツリーの変更を「意図」の単位に束ねて見せる（`tasks.md` T-114）。

## 何を解決するのか

README の原則は「**1 コミット = 1 つの意図**」。守るのが難しいのは、作業していると
複数の意図の変更が作業ツリーに同時に溜まるからで、あとから手で仕分けるのは骨が折れる。

**この開発自体が実例になっている。** 5 つの AI が 1 つの作業ツリーを共有していて、
`git commit -a` は他人の変更を巻き込む。だから「自分の意図の分だけ」を
`git add -- <パス>` で組む必要があり、その組み立てをここが出す。

## 振る舞い

`Nimbus: コミットの分けかたを提案する`。

1. `git status --porcelain --untracked-files=all` を読む（シェルを通さない）
2. 変更を束ねる
3. 束ごとの見出し・理由・`git add -- …` を並べた Markdown を新しいタブで開く

**判断はしない。束ねて見せるだけ。** どれを 1 つのコミットにするかは人が決める。
提案の一枚にもその旨と、「並行セッションでは `git add -A` / `git commit -a` を使わない」
注意を必ず書く。

### 束ねかた

意図を機械が読むことはできないので、**近さ**で代用する。

| 束 | 中身 |
| --- | --- |
| `<機能> まわり` | `core/<名前>.ts` / `<名前>View.ts` / `test/<名前>.test.ts` を同じ束に寄せる |
| その他の変更 | 機能名で束ねられなかったもの（意図が混ざっている可能性を明記する） |
| コア（`src/vs`）の変更 | `nimbus/docs/core-changes.md` への記録も要ることを添える |
| 仕様・確認記録 | 実装と同じコミットに載せる約束なので「上の束のどれかに混ぜる」と促す |
| 台帳（`tasks.md` など） | 同上 |

`core/` と `test/` は**置き場所であって機能名ではない**ので、束ねる前に外す。
これをしないと `test/` 配下がすべて「test まわり」という無意味な束になる（実装して気づいた）。

機能の束は大きい順に並べる。まとまりの強いものから片付けるほうが、残りが見通しやすい。

## 設計

- `extensions/nimbus/src/core/commitSplit.ts` — 束ねかたと出力（VS Code 非依存・単体テスト 9 件）
- `extensions/nimbus/src/commitSplit.ts` — git の実行とタブを開くところ

## 受け入れ条件

- [x] `git status --porcelain` を読む（追跡外・rename・空白入りのパス）
- [x] 同じ機能の実装・ビュー・テストが 1 つの束になる
- [x] コア・仕様・台帳は機能とは分けて最後に出す
- [x] `git add` は**パス指定**で出す（`-A` を出さない）
- [x] 空白や単引用符を含むパスでも壊れない引用
- [x] 変更が無いときに黙らない

## 決めなかったこと・やらないこと

- **自動でコミットする** — 束ねかたは当て推量なので、そのままコミットさせない。
  コマンドを出すところまでにして、実行は人の手に残す
- **hunk 単位での仕分け** — 1 ファイルに 2 つの意図が混ざっている場合は分けられない。
  `core/hunks.ts`（T-113）を使えば技術的には可能だが、`git add -p` の置き換えは
  別の機能として立てるべきなのでここには入れない
- **コミットメッセージの生成** — T-062（リリースノート／コミットメッセージの下書き）の領分
