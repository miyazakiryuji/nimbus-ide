# 承認と、承認前の差分

Claude がツールを使う前に人間が判断する仕組み（旧 F-3 / フォーク F3）。
ファイルを書き換えるツールは、**承認する前に適用後の内容を差分エディタで開く**。

## 何を解決するのか

「あとで差分を見る」では遅い。書き換わってから気づくと、元に戻す作業が始まる。
Nimbus は SDK の `canUseTool` を握り、**判断が終わるまでセッションを止める**。
止まっている間に、これから何が起きるのかを差分として見せる。

## 振る舞い

### 判断の順序

1. **秘匿ファイルの読み取りは、承認を出す前に断る** — 一度読まれた内容は取り消せないので、
   「許可」を押し間違える余地を残さない（[safety](safety.md)）
2. **危険度を判定する** — 自動許可より先。`normal` / `caution` / `danger` の 3 段階
   （判定の中身は [safety](safety.md)）。「常に許可」で `rm -rf` まで素通りさせない
3. **生成物への書き込みなら止めて聞く** — これも自動許可より先（T-139）
4. 危険でなく、設定 `nimbus.permissions.autoApproveReadOnly` が有効で、読み取り専用ツール
   （`Read` / `Glob` / `Grep` / `NotebookRead` / `TodoWrite`）なら自動許可
5. 危険でなく、そのセッションで「常に許可」済みなら自動許可
6. 危険でなく、保存済みの**承認ルール**（`nimbus.permissions.alwaysAllow`）に当たれば自動許可
7. 書き換え系（`Edit` / `Write` / `MultiEdit`）なら**差分を開く**
8. モーダルで聞く（キューモードでは積んで待つ）

### モーダル

| 選択肢 | 意味 |
| --- | --- |
| 許可 | 今回だけ |
| 一部だけ採用 | 変更を選んで、選んだものだけ適用する。**危険な操作では出さない**（T-113） |
| このセッションでは常に許可 | 以後このセッションでは聞かない。**危険な操作では出さない** |
| 今後「〜」は常に許可 | ルールとして設定に残す。**危険な操作では出さない**（T-038） |
| 拒否 | 実行させない |

選択肢は**当てはまるものだけ**出る。「一部だけ採用」は書き換え系で変更が 2 か所以上あるときだけ、
「今後〜」はルールを作れるときだけ。全部そろうのは稀で、たいていは 3 〜 4 個になる。

**Esc で閉じた場合も拒否として扱う。**「答えなかった」を許可に倒すのは危険なので。

`danger` では**自動許可の経路をすべて塞ぐ**（`autoApproveReadOnly` もセッション内の「常に許可」も
効かない）。これは安全機能を入れたときに意図して変えた点で、`caution` / `normal` は従来どおり
3 択のまま。モーダルであること・文言・Esc の扱い・差分を先に開くことは変えていない。

見出しは危険度に応じて変える。危険なものは「危険です」ではなく、**何が危ないのかを名指しする**
（例: 取り返しがつかない操作です — 再帰的な削除）。理由が分からなければ判断できない。

### 承認前の差分

- 設定 `nimbus.permissions.showDiffBeforeApproval`（既定 `true`）が有効なとき、
  書き換え系ツールの入力から「適用後の内容」を組み立て、差分エディタで開く
- **実ファイルにはまだ書き込まれていない。** 承認して初めて Claude が書く
- 差分が出せなくても承認自体は続行する（判断材料が減るだけで、止める理由にはならない）
- 承認・拒否が決まったら差分は閉じる

### 承認の横断キュー（T-010）

セッションが 1 本なら、モーダルがその場で出るので困らない。困るのは**並列に走らせたとき**で、
VS Code のモーダルは 1 枚ずつしか出ないため、後ろで何本のセッションが止まっているのかが
画面のどこにも出ない。放置して他の作業に戻る使いかたでは、これが一番の詰まりどころになる。

**2026-08-18 に役割を絞った（T-263）** — 前面のセッションの承認は会話の中のカードで受ける
（[approval-in-conversation](approval-in-conversation.md)）ので、このビューが出すのは
**いま見ていないセッション・別ウィンドウのぶんだけ**。同じものが 2 か所に並ぶと、
どちらで答えたのか分からなくなる。カードで受けられないとき（コックピットの面が無いとき）は
今までどおり全件を出す。

- サイドバーの「承認待ち」ビューに、**走っている全セッションの承認待ちを 1 か所に集める**。
  ビューにはバッジで件数が出る
- 並びは**危険度の高い順、同じ危険度なら待たせている順**。到着順にしないのは、
  `rm -rf` が 3 番目に埋もれているあいだに、前の 2 件を惰性で許可してしまう並びになるため
- 設定 `nimbus.permissions.queueApprovals`（既定 `false`）を有効にすると、
  **モーダルを出さずにここへ積む**。行のボタンで 許可 / 拒否、右クリックで「今後この種類は常に許可」。
  既定が `false` なので、これまでの使いかたは何も変わらない
- 見出しの「すべて拒否」で、待っているものをまとめて断てる（セッションは止まらない）
- **緊急停止（T-057）は承認待ちも拒否する** — 答えを待つものが残ると、止めたはずのセッションが
  「承認さえすれば動ける」状態でぶら下がり続ける

### 一部だけ採用（T-113）

提案された変更が 1 か所しかないなら、承認は「はい／いいえ」で足りる。困るのは
**1 回の書き換えに、採りたい変更と採りたくない変更が混ざっている**とき。今までは丸ごと拒否して
「ここだけ直して」と言い直すしかなく、往復が 1 回増えていた。

- 承認の選択肢に「一部だけ採用」が出る（変更が 2 か所以上あるときだけ）
- 選ぶと一覧が出る。**既定は全部にチェックが入った状態** — ここまで来た人は「だいたい採りたい」ので、
  外すほうを選ばせるほうが手数が少ない
- **外した変更は元のまま残る。** 消えるのでも、あとで聞かれるのでもない
- 1 つも選ばずに決定した／取りやめた場合は**拒否**として扱う（黙って全部書かせない）

単位はツールごとに変える。同じ「一部だけ」でも自然な区切りが違うため:

| ツール | 単位 | 組み直すもの |
| --- | --- | --- |
| `Write` | いまのファイルと提案された全文の行差分 | `content` |
| `Edit` | `old_string` と `new_string` の行差分 | `new_string`（`old_string` は置き換え対象なので触らない） |
| `MultiEdit` | 個々の編集そのもの | `edits`（採る編集だけ残す） |

行差分は前後の一致部分を削ってから LCS にかける。実際の書き換えは「大きなファイルの一部分」が
ほとんどなので、これで大半は軽く済む。それでも大きすぎる差分（行数の積が 400 万超）は
**1 かたまりに落とす** — 部分採用はできなくなるが、固まるよりよい。

### 生成物への直接編集を止める（T-139）

`build_runner` の生成物（`*.g.dart` / `*.freezed.dart`）やロックファイルを直接書き換えても、
**次に生成し直した瞬間に消える**。消えること自体より、**消えたと気づかないまま先に進む**ほうが
損害が大きい。だから「直しても無駄です」ではなく、**代わりに直す先を名指しする**。

- 書き換え先が生成物なら、**自動許可より先に**止めて聞く
  （自動許可の後ろに置くと黙って通ってしまうため）
- 代わりに直す先を出す — `lib/model.g.dart` なら「`lib/model.dart` を直してから生成ツールを回し直します」
- ロックファイルは直す先がファイルではなくコマンドなので、そちらを言う
  （`pubspec.lock` なら「`flutter pub get` で作り直します」）
- **推測で別のファイルを名指ししない。** 分からなければ「元になっているファイルを直してください」に留める。
  間違った場所を直させるほうが害になる
- 「それでも直接書き換える」は残す（生成物を手で直す正当な場面はある）
- 設定 `nimbus.safety.warnOnGeneratedEdit`（既定 `true`）で切れる

拒否したときは、Claude に**理由と代わりの直し先**を返す。ただ拒否すると、同じ場所を
もう一度書きにくるだけなので。

### 承認ルール（T-038）

「このセッションでは常に許可」はセッションが終われば消える。同じ判断を毎日繰り返さないために、
承認したその場でルールとして残せる。ルールは `nimbus.permissions.alwaysAllow` に文字列で並ぶ。

| 書きかた | 意味 |
| --- | --- |
| `Read` | そのツールなら何でも |
| `Write(*.md)` | 拡張子が `.md` のファイルへの `Write` |
| `Bash(npm test)` | `npm test` で始まるコマンド |

保存先は、フォルダが開いていればワークスペース設定（ルールはリポジトリごとに違うため）、
開いていなければユーザー設定。保存したことは通知で伝え、**「元に戻す」を添える**。

**安全側の約束が 2 つある。**

1. `danger` と判定された操作はルールに関わらず毎回聞く。ルールの候補自体を作らない
2. シェルの制御文字（`;` `&&` `|` `$(` など）を含むコマンドは、**どのルールにも一致させない**。
   `git status && rm -rf /` は `git status` で始まるので、前方一致だけでは安全にならない。
   同じ理由で、そういうコマンドには「今後は常に許可」のボタン自体を出さない

一致は語の切れ目で見る（`Bash(git)` は `github-cli …` を許さない）。

## 設計

- `extensions/nimbus/src/permissions.ts` — `canUseTool` の本体（`createPermissionBroker`）
- `extensions/nimbus/src/proposedEdit.ts` — 適用後の内容を組み立てて差分エディタに出す
- `extensions/nimbus/src/core/describe.ts` — ツール呼び出しを人間が読める一文にする
- `extensions/nimbus/src/core/risk.ts` / `core/secrets.ts` — 危険度判定と秘匿パス（[safety](safety.md)）
- `extensions/nimbus/src/core/approvalRules.ts` — 承認ルールの表現と一致判定（T-038）
- `extensions/nimbus/src/core/approvalQueue.ts` / `approvalsView.ts` — 横断キューの並びと表示（T-010）
- `extensions/nimbus/src/core/hunks.ts` / `core/partialEdit.ts` — 行差分と部分採用（T-113）
- `extensions/nimbus/src/core/generated.ts` — 生成物の判定と「代わりに直す先」（T-139 / T-140）
- `extensions/nimbus/src/core/permissionRules.ts` / `permissionRules.ts` — ルールの言い換えと画面編集（T-028）

設定:

| 設定 | 既定 | 説明 |
| --- | --- | --- |
| `nimbus.permissions.autoApproveReadOnly` | `false` | 読み取り専用ツールを確認なしで許可 |
| `nimbus.permissions.showDiffBeforeApproval` | `true` | 承認の前に差分を開く |
| `nimbus.permissions.offerPartialAccept` | `true` | 変更が 2 か所以上なら「一部だけ採用」を出す（T-113） |
| `nimbus.permissions.queueApprovals` | `false` | モーダルを出さず承認キューに積む（T-010） |
| `nimbus.permissions.alwaysAllow` | `[]` | 確認せずに許可するルール（T-038） |
| `nimbus.safety.warnOnGeneratedEdit` | `true` | 生成物への直接編集を止める（T-139） |

## 決めなかったこと・やらないこと

- **自前の承認インボックス画面** — 旧 Electron 版は持っていたが、既定は VS Code のモーダルに寄せた。
  判断を求める瞬間に前面へ出るぶん、見落としが起きにくい。
  複数セッションを跨いだ承認キューは T-010 で足したが、**既定は今までどおりモーダル**で、
  キューに積むのは設定を有効にしたときだけ（並列に走らせる人にだけ要る機能なので）
- **「常に許可」の永続化** — T-038 で `nimbus.permissions.alwaysAllow` として入れ、
  画面からのルール編集（一覧・追加・削除）は T-028 で入れた（[permission-rules](permission-rules.md)）
- **部分採用の差分プレビュー** — 選んでいる最中に「採用後の全文」を差分エディタへ反映することは
  していない。QuickPick で選ぶあいだ差分を描き替えると、どちらを見ているのか分からなくなるため。
  各変更のプレビューは選択肢の説明文に出す
