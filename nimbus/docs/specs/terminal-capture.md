# ターミナル出力の自動キャプチャ（T-169 / T-106）

テストが落ちた・ビルドが通らない。そのとき人がやっているのは「出力を選択してコピーして、
コックピットに貼る」だけの作業で、その間に何行かは削れるし、色コードや進捗バーの書き戻しが
そのまま混ざる。**その往復を通知のボタン 1 つに畳む。**

VS Code のシェル統合は、コマンド行・作業ディレクトリ・終了コード・出力ストリームを教えてくれる。
素の Claude Code では取れない情報なので、フォークの土台がそのまま効く（`tasks.md` 選ぶ基準 2）。

## 振る舞い

1. ターミナルでコマンドが**失敗した**（終了コードが 0 以外）
2. 「`npm test` が失敗しました（終了コード 1）」という通知が出る
3. **「セッションに投入」**を押すと、コックピットが開いて、コマンド・作業ディレクトリ・
   出力の末尾を添えた指示がそのまま送られる
4. 通知を閉じてしまっても、コマンドパレットの
   **「直近に失敗したコマンドをセッションに投入」**（`nimbus.sendLastTerminalFailure`）で拾い直せる
5. 「今後は知らせない」を押すと設定が切り替わる（通知を出す機能自体を、その場で止められる）

## 実装

- `extensions/nimbus/src/core/terminalCapture.ts` — 整形と判断（VS Code に依存しない純関数）
- `extensions/nimbus/src/terminalWatcher.ts` — シェル統合の口（`onDidStartTerminalShellExecution` /
  `onDidEndTerminalShellExecution` / `execution.read()`）
- `extensions/nimbus/src/extension.ts` — `TerminalWatcher` の生成とコマンド登録
- テスト: `extensions/nimbus/src/test/terminalCapture.test.ts`

## 決めたこと

**声をかける相手を絞る。** 失敗しても人が困っていないものにまで通知を出すと、通知そのものを
切られてしまう。次は黙る。

- 終了コードが **0** のとき（成功）
- 終了コードが **取れない**とき（シェル統合が効いていない）— 成否が分からないものを
  「失敗しました」と言うと、次から信用されない
- **130 / 143**（Ctrl-C・SIGTERM）— 利用者が自分で止めたもの
- `cd` / `ls` / `clear` / `vim` / `less` などの雑多なコマンド（`/usr/bin/ls` の形でも名前で判断する）

**出力は末尾から切る。** 失敗の理由は出力の**終わり**にある。既定 200 行・12,000 文字で、
落とした分は「先頭 N 行は省略」と明示する（黙って落とさない）。1 行が極端に長いログのために、
行数だけでなく文字数でも切る。

**端末の見た目を落とす。** ANSI の色・カーソル移動・シェル統合の制御列（OSC 633）を消し、
`\r` による書き戻し（進捗バー）は**最後に書かれたものだけ**を残す。
制御文字はソースに直接書かず `\u` 表記で置く（見えない文字は編集で壊れる）。

**通知は警告で出す。** 情報通知は数秒で消えるので、押す前に消えたら「ワンクリック」にならない。

**出力は 4 連バッククォートで囲む。** ログの中に ``` が現れても壊れないようにするため。

**読み始めは実行開始時。** シェル統合の `read()` は開始時に読み始めないと取りこぼす（API の注意書き）。
溜め込みは 256KB で頭を捨てる（末尾を残す）。

## ビルドエラーの自動リトライ（T-106）

`nimbus.terminal.autoRetryBuilds` を有効にすると、**通知を出さずに**回す:

1. ビルド・型チェックが失敗する
2. 出力をそのままセッションへ投入する（確認を挟まない）
3. ターンが終わったら、**同じターミナルで同じコマンドを走らせ直す**
4. 通れば「自動で N 回やり直しました」と伝えて終わり。
   直らなければ `nimbus.terminal.maxBuildRetries`（既定 2 回）で止めて人に戻す

**既定は無効。** コマンドを勝手に走らせるのは、それだけで一線を越える。

**走らせ直すのは「利用者が自分で打ったコマンド」だけ。** 新しいコマンドは組み立てないし、
対象も**ビルドと型チェックに限る**（`npm run build` / `tsc` / `cargo build` / `gradlew assemble` /
`flutter build` / `make` など）。`npm install` のような 1 回で終わるもの、`git push` や
`npm run deploy` のような外に出るものは、失敗しても回さない。

**上限は必ず要る。** 直らないまま回り続けるのが一番高くつく（[verify-edits](verify-edits.md) と同じ判断）。

## 設定

| 設定 | 既定 | 意味 |
| --- | --- | --- |
| `nimbus.terminal.captureFailures` | `true` | 失敗したコマンドを知らせる |
| `nimbus.terminal.maxOutputLines` | `200` | 投入する出力の行数（末尾から） |
| `nimbus.terminal.autoRetryBuilds` | `false` | ビルドの失敗を自動で直させ、走らせ直す（T-106）|
| `nimbus.terminal.maxBuildRetries` | `2` | 自動リトライの上限 |

## 残っていること

- シェル統合が効いていないシェル（設定していない zsh・一部の外部ターミナル）では何も起きない。
  「効いていません」と気づける導線は無い
- **T-039 テストランナー / CI 連携** — Test Explorer の結果から直接拾う経路は別（この機能は
  「ターミナルで走らせたとき」に効く）
