# 再現手順の生成

障害のログから、**まず落ちるテスト**を起こす（`tasks.md` T-143）。

## 何を解決するのか

障害を直しにいくときにいちばんやってはいけないのが、**再現しないまま直したつもりになる**こと。
直ったかどうかを確かめる手立てが無いままコードだけ変わり、次に同じものが来たときに
また最初から調べ直すことになる。

エージェントに直させると、この失敗はさらに起きやすい。ログを読んで「たぶんここ」と
直してしまえるので、赤 → 緑の順序が飛ぶ。**先に赤を作る**ための道具。

## 振る舞い

`Nimbus: ログから再現テストを起こす`。ログを貼ると:

1. **状況のまとめ**を開く — 種類・メッセージ・自分のコードで最初に出てくる場所・スタック
2. 「落ちるテストの雛形を作る」か「Claude に再現を頼む」を選ぶ

雛形は落ちた場所の隣に置く（`src/user.ts` → `src/user.repro.test.ts`、
Dart は `test/…_repro_test.dart`）。**既にあるものは潰さない**（開くだけ）。
置き場所が決まらないときは、適当な場所に置かず、開くだけにする。

### 通る形では作らない

雛形は**いまは必ず落ちる**。通るテストを置いてしまうと、
**再現できていないことに気づけないまま「直した」ことになる**。

```
// **このテストは、いまは落ちます。** どんな入力で落ちたかはログに書かれていないので、
// TODO を埋めて「落ちること」を再現してから、直して緑にしてください。
```

**入力までは分からない。**どんな値を渡すと落ちるかはログに書かれていないことが多いので、
そこは `TODO` として残し、**埋めるべき場所を隠さない**。まとめにも
「推測せず、分からないと書く」と明記する。

テストの書き方はプロジェクトから決める（`vitest` / `jest` / `node --test` / Dart）。

## 設計

- `extensions/nimbus/src/core/reproTest.ts` — ログの読み取りと雛形（VS Code 非依存・単体テスト 11 件）
- `extensions/nimbus/src/reproTest.ts` — 貼ってもらう画面とファイルの書き出し

**スタックの読み取りは `core/stackTrace.ts`（T-105）を再利用する。**同じものを二度書かない。

ただし入口の選びかたは変えている。`firstOwnFrame` は「開く先が無いよりまし」として
自分のコードが無ければ先頭のフレームに落ちるが、**再現テストの置き場所としては、
依存の中を指されると困る**。ここでは自分のコードのフレームだけを入口にし、
無ければ「自分のコードの行が見つかりませんでした」と伝える。

メッセージに正規表現・引用符の記号が入っても壊れないようにエスケープする。

- [x] 正規表現・引用符の記号が入っても壊れない
- [x] 既にあるテストを潰さない
- [ ] 実際の障害ログでの確認（未実施）

## 決めなかったこと・やらないこと

- **入力を推測して埋める** — できない。推測で埋めた雛形が「通って」しまうと、
  再現できていないのに直ったことになる。**この機能の目的の逆**
- **Sentry などの API から取りに行く** — 貼れば足りる。認証と設定を持ち込むほどの差が無い
  （T-142 のエラー監視連携は別途）
- **直すところまでやる** — 直すのは Claude の仕事。ここは赤を作るまで
