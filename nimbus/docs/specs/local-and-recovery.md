# ローカル完結・集中モード・詰まったときの立て直し

## 何を解決するのか

3 つとも「**外へ出す／中に留める**」の判断で、誤ると実害が出る。
ローカル完結は**情報**を、集中モードは**通知**を、立て直しは**作業そのもの**を扱う。

対応する tasks.md の項目: T-077（ローカル完結モード）/ T-087（集中モード）/
T-088（失敗時のリカバリ提案）。

## 振る舞い

### ローカル完結モード（T-077）

コマンド **「Nimbus: ローカル完結モードを切り替える」**（`nimbus.localOnly`）。

有効にする前に、**何が止まって何が止まらないかを必ず見せる**。
「外に出ない」と思い込ませるのが一番危ないので。

**止まるもの**
- 監査ログの書き出し（T-050）
- ホットリロードのコマンド実行（T-072）
- フックのドライラン（T-161）
- OS 通知（T-019）— 本文が外部プロセス（`osascript` など）へ渡るため

**止まらないもの**
- **Claude 本体との通信**（これを止めるとエージェントが動かない）
- MCP サーバーへの接続
- Bash などツールの実行（塞ぎたいなら `nimbus.policy.profile` の「隔離」）

### 集中モード（T-087）

タスクに「**T-019 の完了通知と方針が衝突するので、どちらを既定にするかを決める**」とあった件。

**決めた: 集中モードが優先。ただし承認待ちだけは通す。**

集中モードが黙らせたいのは「**終わった**」の知らせであって、「**止まっている**」ではない。
承認待ちを黙らせると作業が進まなくなるので、そこは通す。

設定 `nimbus.focusMode`。通知そのものを切っている（`notifications.enabled: false`）なら、
承認待ちも出さない（利用者の明示的な指定が優先）。

### 立て直し（T-088）

コマンド **「Nimbus: 詰まったときの立て直しを提案してもらう」**（`nimbus.recover`）。

次のどれかに当てはまると「詰まっている」と見る:
- ツールの失敗が **3 回**以上
- 同じファイルを **4 回**以上続けて直している
- 直近のテストが通っていない

**勝手に戻さない。** 見立てと**その理由**を出して、選ばせる:

1. 一旦戻す（チェックポイントへ・T-025）
2. 別解を試す（方針を比べる・T-188）
3. 人間が手を入れる（私が書く番にする・T-190）
4. **このまま続ける**

**理由を言わずに提案しない。** 詰まりの判定は当て推量なので、
外れていると分かれば無視できる形にする。
**選択肢の最後は必ず「このまま続ける」** — 提案が邪魔なときの逃げ道が要る。

## 設計

- `extensions/nimbus/src/core/recovery.ts` — 影響の説明・通知の可否・詰まりの判定。VS Code 非依存
- `extensions/nimbus/src/extension.ts` — コマンドと、既存経路（通知・監査・ホットリロード）への適用

## 決めなかったこと・やらないこと

- **Claude 本体との通信は止めない**（止めると製品が成立しない）。
  ネットワークごと塞ぎたいなら「隔離」プロファイル（T-163）
- **詰まりを自動で止めない。** 提案するだけ。判定は当て推量なので、
  止めると正当な試行錯誤まで邪魔する
- **閾値は設定にしていない。** 3 回・4 回で足りるかを見てから。
  設定にすると「効いていない理由」が増える
