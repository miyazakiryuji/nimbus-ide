# デバッグ面（詰まったときに見るもの）

## 何を解決するのか

エージェントが詰まったとき、画面に出ているのは**起きたこと全部**だった。
「セッションの中身」は畳んだ面、「時系列」は流れ順の面で、どちらも診断パネルにある。
どちらも正しいが、詰まっている最中に知りたいのは 3 つだけで、それが全部の中に埋もれる。

- **何が失敗したか** — 失敗はツール・フック・サブエージェント・セッション・ターンに散っている
- **同じところを回っていないか** — 同じツールを同じ入力で呼び直しているのはループの兆候
- **何を渡して何が返ったか** — ツールの生の入力は、畳んだ面には出ない

あわせて、T-246 で VS Code 標準の「実行とデバッグ」をアクティビティバーから外したまま、
Claude 用の入口が無い状態が続いていた（T-249）。ここがその後釜になる。

## 振る舞い

### アクティビティバー「Nimbus デバッグ」（虫雲アイコン）

独立したコンテナにする。診断パネルと分けたのは**頻度が違う**から。
全部を眺めるのは時々だが、「何が失敗した」は詰まっているあいだずっと見る。
頻度の違うものを同じ段に置くと、どちらも遠くなる（人間工学 E1）。

アイコンは雲を家族マークとして残し、雨粒の代わりに虫を置いた。
24px の単色マスクでは、**細い斜線（雨）と塊（虫の胴）くらい質感が違わないと見分けがつかない**
── 設定アイコン（雲＋歯車）と同じ決めかた。

**失敗が出ると、アイコンにその件数がバッジで出る。** 面を開いていなくても気づけるように。

### 1 面に 4 段

3 つを別々のビューにせず 1 面に畳んでいるのは「セッションの中身」と同じ理由で、
失敗とツール呼び出しは**突き合わせながら**読むため、同じ面にあるほうが速い（人間工学 E2）。

| 段 | 出るもの |
| --- | --- |
| **いま** | 走っているツールと対象。走っていなければ「走っているツールはありません」 |
| **失敗** | ツール（`isError`）／フック（`outcome: error` または終了コード ≠ 0）／サブエージェント（`failed`）／セッション／ターン。**新しいものが上** |
| **繰り返し** | 同じツールを同じ入力で **3 回以上**呼んだもの。多い順 |
| **ツール呼び出し** | 呼び出しと結果の対。**返っていないものも落とさない**（返ってこないこと自体が知りたい事実） |

**理由は推測しない。** 「なぜ失敗したか」は書かない ── 推測を書くと、それが原因だと思われる。
出すのは記録から数えられる事実だけ。

### 押したときに起きること

行は**押したら中身が出る**ところまでで 1 組にする。押せるだけで何も出ないのは、
見えているだけと同じ（T-244）。

- **失敗の行**を押す → 出どころ・時刻・中身を並べた文書が開く
- **失敗の行のインライン「直してもらう」（$(wand)）** → コックピットへ「この失敗を調べて直して」を送る。
  デバッグの出口は「原因が分かった」ではなく「直った」なので、そのまま投げられる形にしてある
- **ツール呼び出しの行**を押す → 渡したもの（生の入力）と返ってきたものが開く。
  **入力はサニタイザ（`maskSecrets`）を通してから**出す ── デバッグのために開いた面が、
  そのまま資格情報の露出になっては困る

### コマンド

| コマンド | どこから |
| --- | --- |
| 「Nimbus: デバッグを開く」 | コマンドパレット（アイコンを押すのと同じ） |
| 「Nimbus: デバッグを更新」 | 面の見出しの $(refresh) |
| 「Nimbus: 失敗の中身を開く」 | 行から／コマンドパレット（引数が無ければ一覧から選ぶ） |
| 「Nimbus: ツール呼び出しの中身を開く」 | 同上 |
| 「Nimbus: この失敗を直してもらう」 | 失敗の行のインラインだけ（パレットには出さない） |

**「失敗の中身を開く」「ツール呼び出しの中身を開く」は、引数が無ければ一覧から選ばせる。**
行から押す経路だけだと、その面を開いている人にしか存在しない機能になる（人間工学 E4）。
逆に「直してもらう」は**送る**動作なので、パレットから一発で撃てないようにしてある。

## 設計

- 数える部分は `src/core/debugInsight.ts`（VS Code に依存しない・モジュールテスト 9 件）。
  面は `src/debugView.ts`
- 入力の同一性は**鍵の順番に依らない**文字列化で見る（`{a,b}` と `{b,a}` を同じと数える）。
  長い本文の末尾差で別物にならないよう 200 文字で打ち切る
- 置き場所は `package.json` の `contributes.viewsContainers` / `views` だけで決まる。
  バッジを出すため `registerTreeDataProvider` ではなく `createTreeView` を使う

### 実測でわかったこと

- **ビューが 1 つだけのコンテナは、見出しが「コンテナ名: ビュー名」になる。**
  GUI の `openContainer` は見出しの完全一致で開けたかを判定するので、
  コンテナ名だけを渡すと一致せず、アイコンを**トグルし続けて閉じたまま終わる**
  （症状は「サイドバーが開けない」で、原因が分かりにくい）
- 常用サイドバーの見出し `Nimbus` は部分一致で拾われるので、
  「Nimbus デバッグ」を足すと `openNimbusSidebar` が誤爆しうる。除外に加えてある

## 受け入れ条件

- [x] アクティビティバーに「Nimbus デバッグ」が出て、**押すと面が開く**（GUI ケース 37）
- [x] 「デバッグを更新」を押しても面が壊れない（GUI ケース 37）
- [x] 「失敗の中身を開く」「ツール呼び出しの中身を開く」が、**無いときは無いと答える**（GUI ケース 37）
- [x] 失敗を出どころごとに拾い、成功を混ぜない（モジュールテスト）
- [x] フックは終わった段でだけ失敗と見なす（モジュールテスト）
- [x] 同じ入力の繰り返しを閾値以上のときだけ出す（モジュールテスト）
- [ ] 失敗が**並んだ状態**での見えかた ── 実セッションが要るので `--with-claude`（07）の経路で見る

## 決めなかったこと・やらないこと

- **VS Code 標準のデバッグ（F5・ブレークポイント）はここに寄せない。** 別物なので混ぜると
  どちらも分かりにくくなる。標準側はアイコンを出していないだけで動く（T-246）
- **「なぜ失敗したか」の判定はしない。** 推測は書かない。直してほしければ
  「直してもらう」でエージェントに投げる
- **キーバインドは割り当てていない。** 頻度からは 1 手にしたいが、既定キーの衝突を
  決めるのは別の話なので分ける（人間工学 E1 の指摘として板に残す）
