# 別のツールの結果と並べて比べる

**タスク**: T-069 / **実装**: `extensions/nimbus/src/core/agentCompare.ts`（判定）,
`extensions/nimbus/src/agentCompare.ts`（VS Code 層） / **テスト**: `src/test/agentCompare.test.ts`

## なぜ

Claude Code をメインに据えたうえで、同じ課題を別のツールにもやらせることがある。
そのとき困るのは「どちらが良いか」ではなく、**どこが違うのかが分からない**こと。
2 つの差分を目で往復して比べるのは、それ自体が仕事になってしまう。

差分ビューはフォークの中にあるので、**違うファイルを左右に並べるところまで**を機械にやらせる。

## どちらが良いかは言わない

良し悪しは、**その課題で何を大事にしているか**で決まる。速さか、読みやすさか、既存の書き方に
合わせることか。機械が決められるのは「両方が同じ行を触った」という事実までで、そこから先は人が決める。

投入する文でも**どちらを採るかは聞かない**。聞けば必ずどちらかを答えるが、それは根拠のある選択ではなく、
聞かれたから出た答えになる。聞くのは 3 つだけ:

1. それぞれが**何をしているか**（やり方の違い。良し悪しではない）
2. **両立するか** — 片方だけが触ったファイルは、そのまま両方採れるか
3. 同じ行を触っている場所で、**選ぶときに効く違い**は何か

## 何を突き合わせるか

比べる相手はどちらも git で指せるもの — **まだコミットしていない手元の変更**か、**ブランチ**。
別のツールの結果は、ブランチかコミットになっていれば比べられる（多くのツールはそうなる）。

起点は両者の `merge-base`（片方が手元の変更なら `HEAD`）。そこからの差分として見る。

| 出るもの | 意味 |
| --- | --- |
| 両方が触ったファイル | ここが見るべき場所 |
| 片方だけが触ったファイル | **そのまま両方採れる**可能性が高い |
| **同じ行**を両方が触ったファイル | ここだけが、片方を捨てる判断の要る場所 |

**ファイルが同じでも、離れた場所を直しているなら両方を採れる。** だから行まで見る。
判定は `git diff -U0` の hunk 見出しから足された行を取り、番号の重なりを数える
（`core/coverage.ts` の `parseAddedLines` を再利用）。

## 出るもの

| コマンド | すること |
| --- | --- |
| `nimbus.compareAgentWork`（別のツールの結果と並べて比べる） | 2 つを選ぶ → 違いの一覧 → 同じ行を触ったファイルを差分で開く／違いを整理させる |

## 確認項目

- [ ] 手元の変更とブランチを比べられる（同じものは 2 度選べない）
- [ ] 片方だけが触ったファイルが、それぞれの側に分かれて出る
- [ ] 同じファイルでも行が離れていれば「同じ行」に数えない
- [ ] 改名（`R100 old new`）が**新しい方**のパスで出る
- [ ] 違いが無いとき「違いはありません」で終わる
- [ ] 投入する文に「どちらが良いか」を求める文が入っていない
