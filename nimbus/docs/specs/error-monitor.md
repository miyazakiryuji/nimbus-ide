# 監視ツールの障害を取り込む

Sentry などの障害を、**影響の大きさと足あた**つきでセッションに投入する（`tasks.md` T-142）。

## 何を解決するのか

スタックトレースは「**どこで**落ちたか」しか言わない。監視ツールはそれに加えて
2 つを持っていて、どちらもスタックからは絶対に出てこない。

1. **どれくらい効いているか**（件数・影響人数・初回/最終・リリース）→ **直す順番**を変える
2. **何をしたら落ちたか**（breadcrumbs＝操作の足あと）→ **再現の入力そのもの**になる

2 番目が本命。「4,021 回 / 137 人」だけでも優先順位は決まるが、
`/home → /users` → `button#invite` → `POST /api/invite` という足あとがあれば、
**再現テストがそのまま書ける**。

## 振る舞い

`Nimbus: 監視ツールの障害を取り込む`。issue の JSON を貼ると:

1. **影響の大きさを最初に**出す（直す順番を決めるのがここだから）
2. リリース・環境・初回/最終発生・元の記録へのリンク
3. **落ちるまでの足あと** — 「再現の入力はここから作れます」と添える
4. 「Claude に再現を頼む」で、**まず再現するテスト**を書かせる

足あとは**新しい方（落ちた瞬間に近い方）を残して** 12 件まで。
省いたときは「古い N 件は省略」と言う。足あとが無いときも「入っていませんでした」と言う
（黙って省くと、そもそも足あとがあったのか分からない）。

**解決済みの記録には、直しにいく前に確かめさせる。**
`status` が無いものを解決済みと決めつけることはしない。

### 数を嘘にしない

Sentry は件数を**文字列で**返すことがある（`"count": "4021"`）。
数として読めないものは `undefined` にして、「影響の大きさは分かりません」と言う。
**0 とは言わない** — 0 回起きた障害は存在しないので、0 と出た時点で嘘になる。

読めない JSON は `undefined`。中途半端に読むと、件数や影響人数が嘘になる。

## 設計

- `extensions/nimbus/src/core/errorMonitor.ts` — JSON の読み取りと整形（VS Code 非依存・単体テスト 12 件）
- `extensions/nimbus/src/errorMonitor.ts` — 貼ってもらう画面

**重複を作らないための分担**（同じ「障害」を 3 つが別々の面から扱う）:

| モジュール | 扱うもの |
| --- | --- |
| `core/crashLog.ts`（T-074） | 実機クラッシュの**テキスト** |
| `core/reproTest.ts`（T-143） | スタックから**落ちるテスト**を起こす |
| `core/errorMonitor.ts`（ここ） | **JSON にしか無いもの**（件数・人数・リリース・足あと） |

## 受け入れ条件

- [x] 件数・影響人数・リリース・環境を取り出す
- [x] 件数が文字列でも数として読む
- [x] 足あとを読む（`message` が無くても `data.url` / `type` から拾う）
- [x] `metadata` しか無い形でも題名を作る
- [x] 読めないものは `undefined`（中途半端に読まない）
- [x] `status` が無いものを解決済みと決めつけない
- [x] 影響が分からないときに 0 と言わない
- [x] 足あとは新しい方を残し、省いたことを言う
- [ ] 実際の Sentry の issue での確認（未実施）

## 決めなかったこと・やらないこと

- **API から取りに行く** — 貼れば足りる。認証・トークンの置き場所・組織設定を持ち込むほどの
  差が無い。**秘密情報を Nimbus に預けさせない**ほうが、この製品の性格に合う
- **障害を解決済みにする** — 監視ツール側の状態は変えない。直ったかどうかの判断は人のもの
- **Sentry 以外の形式を個別に足す** — 形式ごとに読み取りを増やすと、誤読がそのまま
  「件数の嘘」になる。まず Sentry の形（issue / event）を確実に読む
