# 脆弱性の警告を直す順に並べる

`npm audit` の結果を、手を付けられる順にする（T-121）。

## 何を解決するのか

`npm audit` は**全部まとめて出る**ので、どれから手を付けるかが分からない。しかも `--force` を
打つと破壊的変更ごと当たって、別のものが壊れる。

## 振る舞い

コマンド「脆弱性の警告を直す順に並べる」（`nimbus.openVulnFixPlan`）。

- `npm audit --json` を実行して読む（**脆弱性があると終了コードが 1 になる**ので、
  エラーでも出力を読む）
- 3 つに分ける

  | 区分 | 何をすればいいか |
  | --- | --- |
  | そのまま上げられる | `npm audit fix` で当たる。今日やる |
  | 破壊的変更を含む | 1 つずつ変更履歴を見て上げる。時間を取る |
  | 直し方が示されていない | 上流待ち。使うのをやめるかの判断が要る |

- **深刻さより先に「今日できるか」で分ける。** 深刻でも破壊的変更が必要なら今日は直せない。
  今日できることを先に見せたほうが、実際に減る
- 各区分の中は深刻な順
- **`npm audit fix --force` を使わないよう明記する**（何が壊れるか分からないまま当たるため）
- **直す操作はしない。** コマンドは人が打つ

## 設計

- `extensions/nimbus/src/core/vulnFix.ts` — 読み取りと並べ替え（VS Code 非依存）
- `extensions/nimbus/src/vulnFix.ts` — `npm audit` の実行と表示

出力の形が変わっても落ちないよう、緩く読む（読めない項目は飛ばす）。

## 受け入れ条件

- [x] `npm audit --json` を読む（壊れた JSON では空を返す）
- [x] そのまま上げられる／破壊的／直せない、に分ける
- [x] 深刻でも破壊的なら「今日できる」に入れない
- [x] 各区分の中を深刻な順に並べる
- [x] `--force` を使わないよう明記する
- [ ] 画面確認（実際の警告で試す・未実施）

単体テスト: `extensions/nimbus/src/test/vulnFix.test.ts`（8 件）

## 決めなかったこと・やらないこと

- **自動での修正** — `npm audit fix` すら打たない。何が上がるかを見てから人が打つ
- **Dart / pub 側** — `pub` に同等の仕組みが無い。まず npm から
