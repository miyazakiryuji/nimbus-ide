# 移行前後の等価性確認（T-179）

ライブラリの入れ替えや作り直しで一番怖いのは、**気づかないうちに振る舞いが変わる**こと。
差分を読んでも分からないし、テストが無ければ気づきようがない。

防ぐ道具は 1 つしかない — 移行の**前**に、いまの振る舞いをそのまま写したテストを書いておくこと。
仕様として正しいかは問わない。正しくないところも含めて、いまのとおりに写す
（characterization test）。移行後に同じテストが通れば、変わっていないと言える。

## 振る舞い

**「移行前の振る舞いを固定する」**（`nimbus.captureBehavior`）

開いているファイル（選択範囲があればそこ）を対象に、次の条件つきでテストを頼む:

- **仕様として正しいかは問わない。** 正しくない挙動も、いまのとおりに写す
- 入力と出力の組を挙げ、**境界と例外**（空・null・上限・エラー時）を落とさない
- 実装の中身ではなく、**外から見た振る舞い**を書く

作業ツリーが既に書き換わっているときは、**`HEAD` の内容**を「移行前」として渡す
（そのことを指示の中に明記する）。「前」を取り違えない。

**「移行後の等価性を確かめる」**（`nimbus.verifyEquivalence`）

落ちたテストを「直すもの」ではなく**変わった証拠**として扱わせる:

1. **意図した変更** — なぜ変えたのか、根拠は何かを書いたうえでテストを更新する
2. **意図していない変更** — 実装の方を直す

分からないものは分からないと書かせる。**通すためにテストを緩めない。**

## 実装

- `extensions/nimbus/src/core/equivalence.ts` — 頼み方（純関数）
- `extensions/nimbus/src/equivalence.ts` — エディタと `git show HEAD:<file>`
- テスト: `extensions/nimbus/src/test/equivalence.test.ts`

## 決めたこと

**この機能の本体は「頼み方」。** テストを生成するのは Claude で、Nimbus がやるのは
**外してはいけない一文を毎回入れること**。「正しい仕様を書いて」と言った瞬間に
characterization test ではなくなる。

**貼るのは 300 行まで。** 超えたら「残りはファイルを読んでください」と添える。

**「移行前」は `HEAD`。** 作業ツリーが既に変わっていれば、そちらではなく `HEAD` を渡す。

## 確認すること

- [ ] ファイルを開いて「移行前の振る舞いを固定する」で、条件つきの指示が送られる
- [ ] 選択範囲があれば、その範囲だけが渡る
- [ ] ファイルを書き換えた状態で実行すると「HEAD の内容を渡しています」と入る
- [ ] git 管理外の新規ファイルでも落ちない
- [ ] 「移行後の等価性を確かめる」で、落ちたテストの仕分けを求める指示が送られる
