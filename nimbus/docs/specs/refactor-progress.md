# 段階的リファクタの進捗管理（T-111）

大きな置き換えが途中で止まるのは、面倒だからではなく**どこまでやったか分からなくなる**から。
「全 120 箇所中 48 箇所置換済み、残り 72」が見えていれば、翌日でも、別のセッションでも再開できる。

## 振る舞い

**「置き換えを追いかける」**（`nimbus.trackRefactor`）

1. 残りを数えるパターン（拡張正規表現）と、置き換えの名前を入れる
2. **いまの件数を分母として控える**（途中から数え始めても「残り」は正しく出る）

**「置き換えの進捗を見る」**（`nimbus.refactorProgress`）

```
██░░░ 48/120（残り 72）  getUserById を廃止
```

選ぶと「続きを頼む」か「追跡をやめる」。続きを頼むと、**残りの多いファイルから**潰す指示が
コックピットへ送られる。残り 0 になっていれば、そのまま追跡を終われる。

## 実装

- `extensions/nimbus/src/core/refactorProgress.ts` — 数え方と見せ方（純関数）
- `extensions/nimbus/src/refactorProgress.ts` — `git grep -c` と `workspaceState`
- テスト: `extensions/nimbus/src/test/refactorProgress.test.ts`

## 決めたこと

**数えるのは `git grep -c`。** `.gitignore` を尊重するし、速い。ワークスペース全体を
読み直す実装にすると、大きなリポジトリで使い物にならない。

**分母は「始めたときの件数」で固定する。** 作業中に対象が増えることはある（新しいコードが
古い書き方で足される）。そのとき分母まで動くと、進んでいるのに数字が戻って見える。
置換済みが負にならないよう 0 で止める。

**保存先は `workspaceState`。** 置き換えはそのリポジトリの話なので、ワークスペース単位で持つ。

**続きを頼む文に「一度に全部やらないでください」を入れる。** 120 箇所を 1 ターンで
置換させると、レビューできない差分ができる。数ファイルずつ、テストを挟みながら進めさせる。

**残っている場所は多い順。** 手を付ける順番はそれで決まる（1 箇所ずつ散っているファイルは後回し）。

## 確認すること

- [ ] パターンを入れて追跡を始めると、いまの件数が出る
- [ ] 当たらないパターンでは「当たる箇所がありません」と出て、追跡は始まらない
- [ ] いくつか置き換えたあと進捗を見ると、残りが減っている
- [ ] 「続きを頼む」で、残りの多いファイルから並んだ指示が送られる
- [ ] 残り 0 になると「追跡をやめる」だけが出る
- [ ] ウィンドウを閉じて開き直しても追跡が残っている

## 残っていること

- **T-110 大規模な一括変更**（パッケージ横断の追従）は別。こちらは「数える」側だけ
- パターンは正規表現をそのまま渡す。書き間違えると 0 件になるだけで、検証はしていない
- 複数ルートのワークスペースでは最初のフォルダだけを数える（T-173 と一緒に直す）
