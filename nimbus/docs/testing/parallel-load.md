# 並列で走らせたときの破損と遅延（実測）

**タスク**: T-248 / **測るもの**: `nimbus/scripts/bench-parallel.mjs` /
**仕様**: [session-registry](../specs/session-registry.md)

```bash
npx tsc -p extensions/nimbus                 # out/ を作ってから
node nimbus/scripts/bench-parallel.mjs       # 既定は書き手 4 プロセス × 200 件
```

**対策より先に測った。** 直す前に測らないと、直っていないものを直したことにしてしまう。
測ったのは Nimbus 自身が持っている共有の書き込み口だけで、Claude の API そのものの速さは測っていない
（課金が発生するうえ、こちらでは制御できない）。

## 2026-08-18 / macOS 15 (arm64) / 書き手 4 プロセス × 200 件

| 書きかた | 残った件数 / 期待 | 消えた件数 | 所要 ms |
| --- | --- | --- | --- |
| 監査ログ：読んで書き直す（旧） | 3 / 800 | **797** | 146 |
| 監査ログ：追記だけ（新・T-250） | 800 / 800 | 0 | 49 |
| 台帳：1 つの JSON に全部（旧） | 400 / 800 | **400** | 147 |
| 台帳：1 セッション 1 ファイル（新・T-247） | 800 / 800 | 0 | 119 |

**「読んで書き直す」は、並列にした瞬間にほぼ全部消える。** 800 行書いて 3 行。
最後に書いた人の内容だけが残るので、そういう壊れかたになる。
しかも遅い — 消えているのに 3 倍時間がかかっている。

## ファイルが育つと、1 行の追記はどれだけ遅くなるか

| 既にある行数 | 読んで書き直す ms | 追記だけ ms |
| --- | --- | --- |
| 0 | 0.45 | 0.05 |
| 1,000 | 6.60 | 0.05 |
| 10,000 | 11.15 | 0.15 |
| 50,000 | 12.20 | 0.15 |

読んで書き直す方式は**ログが育つほど遅くなる**（1 日使えば数万行になる）。追記は伸びない。

## イベントの畳み直しは、間引く必要があるか

面（タイムライン・活動）は、イベントが来るたびに畳み直している。並列で走らせると
イベントの本数が倍々になるので、ここが効くかどうかを測った。

| 溜まったイベント数 | 1 回畳むのに ms |
| --- | --- |
| 100 | 0.05 |
| 500 | 0.05 |
| 1,000 | 0.10 |
| 2,000 | 0.10 |

**要らなかった。** 保持上限の 2,000 件でも 1 回 0.1ms で、間引く仕組みを足すほうが害が大きい。
測らずに「重そうだから」で throttle を入れていたら、表示が遅れるだけの改悪になっていた。

## やったこと・やらなかったこと

| | 判断 |
| --- | --- |
| 監査ログを追記だけにする | **やった**（T-250）。797 件の消失 → 0 |
| 台帳を 1 セッション 1 ファイルにする | **やった**（T-247）。400 件の消失 → 0 |
| 同時実行を台帳で横断的に数える | **やった**（T-251）。別ウィンドウのぶんも同じ上限に入る |
| 書き込みを 1 本のキューへ直列化する | **やらない**。書き手を分ければ競合しないので、直列化する対象が無い |
| 面の畳み直しを間引く | **やらない**。2,000 件でも 0.1ms（上の表） |
| SDK 呼び出しのバックオフ | **保留**。上限で絞ったうえで、実際に 429 を踏んでから決める（踏まずに書くと当てずっぽうになる） |
