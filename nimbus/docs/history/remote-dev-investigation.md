# リモート開発の前提調査（T-084）

- 実施日: 2026-08-13
- 目的: `tasks.md` T-084 が「**OSS 代替の調査が前提**」としているので、まず調査だけを行う
- 結論: **土台は揃っている。足りないのは「接続する拡張」と「リモート側の Claude Code」の 2 つ。**

## 何を確かめたか

### 1. フォークにリモートの土台は残っているか → **残っている**

Code - OSS のリモート拡張ホスト（REH = Remote Extension Host）の仕組みは、
フォークにそのまま入っている。

| 確かめたこと | 結果 |
| --- | --- |
| `src/vs/server/` | ある（`node/` と `test/`） |
| REH のビルドタスク | `npm run minify-vscode-reh` / `minify-vscode-reh-web` が `package.json` にある |
| REH の対象プラットフォーム | `build/gulpfile.reh.ts` に win32 / darwin / linux（x64・arm64）と alpine |

つまり**「リモート側で動くサーバ」は自分でビルドできる**。ここは MS のライセンスに触れない
（Code - OSS の一部なので）。

### 2. MS の Remote-SSH / Dev Containers は使えるか → **使えない**

`tasks.md` の但し書きどおり。これらは Microsoft が VS Code 製品向けにのみ配布している拡張で、
**フォークでの利用は利用規約で認められていない**。Marketplace 自体も使えない
（`保留・やらないと決めたこと` に既に記録済み）。

### 3. OSS 代替は入れられるか → **入れられる（ギャラリーは Open VSX を向いている）**

`product.json` の `extensionsGallery` は **Open VSX** を指している。

```
serviceUrl = https://open-vsx.org/vscode/gallery
itemUrl    = https://open-vsx.org/vscode/item
```

`open-remote-ssh` 系の OSS 拡張は Open VSX で配布されているので、**インストール経路はある**。
ただし**実際に接続できるかはこの調査では確かめていない**（実機の SSH 先が要るため）。
「入れられる」ことと「動く」ことは別なので、そこは分けて記録しておく。

### 4. Nimbus 拡張はリモート側で動くか → **既定で動く。それが望ましい**

`extensions/nimbus/package.json` に `extensionKind` の指定が無い。VS Code の既定は
**workspace 側（＝リモート）**なので、リモートに繋いだとき **Nimbus の拡張はリモートで動く**。

これは狙いどおり。Claude Code は**コードのある側**で走ってほしいので、
UI だけ手元に残して実行はリモート、という形が自然に出る。

## 実装に入る前に決めること

土台があるので、残る問題は 2 つだけ。**どちらも技術ではなく段取りの問題**。

### (a) リモート側に Claude Code が要る

`claudeExecutable.ts` は探索順（設定 → SDK 同梱 → PATH と既知の場所）で実行ファイルを探す。
リモートで動く以上、**この探索はリモート側で走る**。つまり:

- リモートに Claude Code が入っていなければ動かない
- 認証もリモート側で済んでいる必要がある（`~/.claude` はリモートのもの）

いまの `reportMissingExecutable()` は手元向けの案内なので、**リモートのときは
「繋いだ先に入れてください」と言い分ける**必要がある。ここは小さな改修で済む。

### (b) どの OSS 拡張を薦めるかは、利用者に押しつけない

Nimbus が特定の OSS リモート拡張を同梱・既定化すると、その拡張のメンテ状況を
Nimbus が背負うことになる。**「Open VSX から入れてください」と案内するに留める**のが
今の Nimbus の作りに合っている（Marketplace を使わない判断と同じ考えかた）。

## この調査でやらなかったこと

- **実機での接続確認** — SSH 先と devcontainer が要る。**入れられることと動くことは別**なので、
  ここを確かめずに「対応済み」とは書かない
- **REH のビルド** — 数十分かかるうえ、確かめたいのは「タスクがあるか」だったので、
  存在の確認までにした
- **`open-remote-ssh` の中身の評価** — メンテ状況・ライセンス・実際の動作は、
  薦めると決めてから見るべきこと。決める前に評価しても判断が先走る

## 追記（2026-08-13・別セッションの指摘を検証）

調査時に「②は実機の SSH 先が要る」と書いたが、**それは正確ではなかった**。

| 確かめたこと | 結果 |
| --- | --- |
| このマシンで Docker が動くか | **動く**（`/usr/local/bin/docker`・`docker info` 応答あり） |
| REH の linux 版ビルド対象があるか | **ある**（`build/gulpfile.reh.ts` の `BUILD_TARGETS` に `linux` × `x64` / `arm64`） |

VS Code から見れば **devcontainer も SSH と同じ「リモート」**で、
`vscode.env.remoteName` には `dev-container` / `attached-container` が入る。
つまり **SSH の実機が無くても、①が実際に効くかは確かめられる**。

**それでも今日は回さない。** 理由が変わっただけで、止まっていること自体は変わらない:

1. **REH の linux 版ビルドが重い**（数十分規模）
2. **複数のセッションが同じ作業ツリーでコンパイルしている。**
   ここで大きなビルドを回すと、他セッションの `out/` を巻き込んで
   「再実行すると消えるテスト失敗」を量産する
3. **接続には Open VSX の OSS リモート拡張を先に入れる必要がある。**
   どれを薦めるかは決めない方針なので、ここは利用者の選択が要る

**保留の理由を「SSH 実機が要る」から上記に直した。**
保留の欄は「同じ議論を別のセッションが蒸し返さないために置いてある」ので、
理由が事実とずれていると役に立たない。Docker があるのに「実機が無い」と書いてあれば、
次に読む人は当然そこを突く。

## 次にやるなら

**上の追記のとおり、3 は「SSH の実機が無いから」ではなく「REH のビルドが重く、

devcontainer でよいので、ツリーが空いたときに回せば確かめられる。
