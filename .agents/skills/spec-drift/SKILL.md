# 実装と記述のズレを見つける

ドキュメントが実装から遅れると、**次のセッションが古い記述を正しい仕様だと思って作業を始める**。
並行開発ではここが最初に壊れる。定期的に突き合わせる。

## 手順

### 1. 機械で分かる分を先に潰す

```bash
node nimbus/scripts/doctor.mjs docs contributes
```

存在しない設定名への言及、壊れたリンク、宣言と実装のズレはここで出る。

### 2. 突き合わせる対象を集める

| 記述 | 場所 | 何の正本か |
| --- | --- | --- |
| 仕様書 | `nimbus/docs/specs/<機能>.md` | 「今どう動くべきか」 |
| README | `README.md`（できること・設定の表・使いかた） | 利用者から見た振る舞い |
| ゆあのガイド | `extensions/nimbus/src/help/yua.ts` の `NIMBUS_GUIDE` | 製品内ヘルプが answers に使う知識 |
| コア変更の台帳 | `nimbus/docs/core-changes.md` | upstream へ入れた変更 |
| タスク | `tasks.md` | 完了・未着手の状態 |
| 確認記録 | `nimbus/docs/testing/` | 受け入れ条件をどう確かめたか |

### 3. 読み比べる（ここが人の仕事）

実装の入口から追いながら、次を問う。

- **書いてあるのに無い** — 記述された設定・コマンド・ビュー・振る舞いが実装に無い
- **あるのに書かれていない** — 実装した機能が README / 仕様書 / ゆあのガイドのどれにも無い
- **意味がズレている** — 名前は合っているが既定値や条件が違う（例: 既定でオンのはずがオフ）
- **前提が古い** — 「〜は未実装」「〜が必要」といった記述が、もう当てはまらない
- **タスクが取り残されている** — 実装済みなのに `tasks.md` の 完了 へ移っていない

特に **ゆあのガイド**は忘れられやすい。ここが古いと、製品内ヘルプが利用者に嘘をつく。

### 4. 直す

- 実装が正しいなら記述を直す（ほとんどはこちら）
- 記述が正しいなら実装を直す。すぐ直せないなら `tasks.md` に 1 行足して残す
- **同じコミットで**直す。「あとでまとめて」は成立しない

## 見つかったら記録する

大きなズレは、なぜ起きたかを 1 行で `nimbus/docs/testing/` の該当記録に残す。
同じ壊れ方を繰り返さないための材料になる。
