# 敵対的試験と、Codex との協調

**総合試験は「決めた道を通ると、決めたとおりに動く」ことしか見ない。** 壊れるのはいつも
決めていない道 — 前のケースが残した面、押してはいけない順番、型が違う 1 バイト、無いはずの空、
極端な寸法 — で、そこは緑のまま素通りする。

2026-08-31 の実測（T-345）: 総合試験が **63/63 緑**だったビルドに敵対束を当てたら
**16 本中 11 本が落ち、11 本すべてが本物の不具合だった**（ハーネスの都合による赤は 0 本）。
そのうち 1 本は「画像を入力欄へドラッグすると添付が 2 枚溜まる ＝ 送れば二重に課金」で、
敵対的な使いかたですらない普通の操作だった。

## 1. いつ使うか

- 利用者が「敵対的な試験」「わざと壊してみて」と言ったとき
- 総合試験が緑なのに、実際の利用で不具合が出ているとき
- リリース前（総合試験の一環として 1 回。並びは `nimbus-test` スキルの「総合試験」の節 —
  GUI 全件 → `--untrusted` → **`--adversarial`** → doctor → デグレチェックが締め）
- 既存の振る舞いを変える直しを入れる前（Codex の節だけでもよい）

普段の実装後には**使わない**。該当ケースの `--only` で足りる（T-325）。

## 2. 走らせかた

敵対的ケースは**既定の全件に混ぜない。** わざと壊しにいく束なので、混ぜると「普段の緑」が
読めなくなり、並行している他のセッションの判断材料を汚す。

```bash
bash nimbus/scripts/package-app.sh --copy /tmp/nimbus-gui-app       # 固めて写しを作る
NIMBUS_APP=/tmp/nimbus-gui-app/Nimbus.app \
  node nimbus/tests/gui/run.mjs --packaged --adversarial            # 敵対束（全 16 本）
NIMBUS_APP=/tmp/nimbus-gui-app/Nimbus.app \
  node nimbus/tests/gui/run.mjs --packaged --adversarial --only adv-05   # 1 本だけ
```

分岐は `run.mjs` の 1 行だけ（`Boolean(c.adversarial) === flag('adversarial')`）。
ケース側は `export default { name: '…', adversarial: true, async run(page, ctx) { … } }`。
**`adversarial: true` を付け忘れると既定の全件に混ざる。最初に書く。**

設計書は [`nimbus/docs/testing/adversarial.md`](../../../nimbus/docs/testing/adversarial.md)
（観点ごとのケース一覧・根拠のファイル:行・却下した案とその理由）。

## 3. 観点 — どこを叩くか

案を出すときは、この 8 つを順に当てる。**「連打してみる」だけの案は書かない** —
同期処理なら必ず緑になって何も証明しない。**隙間が実在するものだけを撃つ。**

| 観点 | 狙う壊れかた |
| --- | --- |
| **順番と持ち越し** | 同じ操作の 2 回目 / 別の面 / 別の入口。「単独では通り、束では落ちる」が生まれる場所 |
| **連打と競合** | 旗を読んでから書くまでに `await` が挟まる経路。1 tick の 2 連打で両方が同じ枝を走る |
| **敵対的な入力** | 長い 1 語・改行・絵文字・RTL・制御文字・HTML のかけら・`../`。**エスケープされずに DOM 要素になる**経路と、保存 → 読み直しで化ける経路 |
| **状態を外から壊す** | 保存ファイルを壊れた JSON / 型違い / 参照先の消えた id に書き換えて読み直す |
| **空と欠損** | git 無し・コミット 0 件・実行ファイル無し・0 件・権限無し。**無いものを無いと言えるか** |
| **寸法の極端** | 最小幅・サッシを端まで・全画面の往復。**素の操作で壊れるなら、それはズームの話ではない** |
| **量** | 上限そのものの件数を一度に。上限は「実際に通る道」であって例外ではない |
| **中断とキャンセル** | Escape・途中で閉じる・書きかけで別へ移る。**まだケースが無い**（足すなら 8 節の手順で） |

設計書 `adversarial.md` §3 は同じ観点を別の名前で並べている — 「状態を外から壊す」＝**壊れた記録**、
「連打と競合」＝**速さと競合**、「敵対的な入力」＝**敵意のある入力**、「空と欠損」＝**空と欠け**。
突き合わせるときはこの対応で読む。

## 4. ケースを書くときの掟

ここを外すと、束が丸ごと死ぬか、偽の緑になる。

1. **ネイティブのモーダルを出さない。** 出た瞬間に以後の全操作が固まる。
   `showOpenDialog` に至るボタン・`{ modal: true }` の確認・未保存の無題エディタを閉じる操作に触れない
2. **後始末は `try { … } finally { … }`。** 敵対ケースは落ちるのが目的なので、
   `ctx.expect` の後ろに書いた後始末は**実行されない**。finally の中で `ctx.expect` を投げない
3. **絶対数を数えない。** 「札が 1 枚」「タブが 0 枚」は束の並び次第で崩れる。
   自分が置いたものを**名前で探して**判定する
4. **落ちること自体を目的にしない。** 「Nimbus はこう振る舞うべき」という期待を書き、
   そこから外れたら落ちる形にする。**決まっていない振る舞いを試験で決めない**（→ 5 節 ①）
5. **偽の緑を潰す関門を先に置く。** 前提が作れなかったときに `ctx.expect` を 1 度も通らずに
   抜ける道があると、何も確かめずに緑になる。「毒が届いたか」を先に確かめてから本判定へ進む
6. **失敗メッセージに実測値を埋める**（枚数・px・文字列の先頭）。「見つからない」だけでは直せない
7. **課金しない。** 送信・Enter・「開始」は押さない。1 ケース 60 秒以内
8. 触ってよいのは `ctx.workspace` と `ctx.userDataDir` の下だけ

## 5. 落ちたときの切り分け

**赤 ＝ 不具合ではない。** 3 種類ある。**②を疑う前に①を疑う。**

### ① 仕様が決まっていない
仕様書に記述が無い、あるいはコードのコメントが逆を宣言している。
→ **直さない。ケースも直さない。** 板に「決めていないこと」として起こし、利用者に判断を仰ぐ。
決まったら**仕様書の追記とケースを同じコミットで**入れる。

### ② ハーネスの都合
単独（`--only`）で通り、束で落ちる。または落ちかたが毎回変わる。
→ **製品ではなく試験を直す。** 直すのは (a) 落ちたケースの finally、(b) 前のケースの finally、
(c) 判定を「自分が置いたものを名前で探す」形へ。直したら**単独と束の両方**で通ることを確かめる。

### ③ 本物の不具合
単独でも束でも同じように落ち、経路をコードで追える。
→ 板に T 番号を起こし、**直しは別のコミット**（試験を足すコミットに製品の修正を混ぜない）。
直したら回帰を 1 本足し、**テストの見出しに T 番号を書く**。

## 6. 今回いちばん効いた 4 つ（実測つき）

### 副次の判定は、本命が緑になるまで**一度も走らない**
adv-10 は「1 枚落として 2 枚溜まる」で落ちていたので、その後ろの「札の幅」判定に
**一度も到達していなかった**。本命を直した瞬間に 2 つめ（**面の幅 559px に対して札が 1,420px**
まで伸び、×（外す）が画面の外へ出る）が出た。
→ **直すたびに敵対束を回し直す。** 1 回直して 1 回回す。

### 既存の振る舞いを変える前に、それを守っているケースを `grep` で洗う
T-356 で「Home の開閉を面ごとに持つ」を素直に入れたら、ケース 59 の確認項目
「開いた状態がタブの面にも引き継がれる」を壊した（GUI 全件 63/63 → 55/63）。
**引き継ぎと独立は別の話**だった。`grep -l` 1 回で気づけた。
→ 変える前に `grep -rl "<その振る舞いの言葉>" nimbus/tests/gui/cases/ nimbus/docs/specs/`。

### 入口を移す変更は、その入口に依存する**全ケース**を直す
`≡` の廃止（`d02cd68fc1f`）で、ケース 47 / 54 / 57 が `#homeToggle` を掴んだまま置き去りになった
（59 だけ直されていた）。47 は `--with-claude` 限定なので既定では素通りする**偽の緑**だった。
→ セレクタや入口を消したら `grep -l "<消したもの>" nimbus/tests/gui/cases/`。

### 「退行か、環境か」は A/B で決める。数字だけで判断しない
GUI 全件が 63/63 → 54/63 に落ちたので退行を疑ったが、**直し前のビルドで同じ日に回したら 55/63**
で、失敗 7 件が共通だった。同じバイナリが数時間前は 63/63。劣化したのはコードではなく試験の
安定性だった（→ T-359）。
→ **直す前のビルドを消さない**（`package-app.sh --copy /tmp/nimbus-gui-appN` で番号を振って残す）。
疑わしいときは同じ日に両方回して、**失敗の集合を `comm` で比べる**。

```bash
grep "^  ✖" 直し前.log | sed 's/^  ✖ //' | sort > /tmp/a.txt
grep "^  ✖" 直し後.log | sed 's/^  ✖ //' | sort > /tmp/b.txt
comm -13 /tmp/a.txt /tmp/b.txt   # 直し後だけ落ちたもの ＝ 退行の候補
```

## 7. Codex を第二の目として使う

**同じ穴を 2 回覗いても、同じものしか見えない。** 自分（と自分が出した subagent）は前提を
共有しているので、**前提そのものが間違っているときに気づけない**。別系統のモデルに読ませると、
そこが出る。

### 使うとき
- **既存の振る舞いを変える直し**を入れる前（いちばん効く）
- API の有無・プラットフォームの制約など、**事実確認が要る**とき
- 直しの筋に自信が持てないとき

### 使いかた

```bash
cat > /tmp/prompt.txt <<'EOF'
あなたは <プロジェクト> のレビュアです。**実装はしないでください。読んで意見だけ返してください。**

## 1. <不具合の名前>（ファイル:行）
実測の症状: …
入れようとしている直し: …
聞きたいこと: <具体的な問い。「見落としがちな穴は」「もっと素直な直しかたは」>

回答は日本語で、各件「結論 → 理由 → 具体的な指摘」の順に簡潔に。コードは必要な断片だけ。
EOF
codex exec --skip-git-repo-check -c model_reasoning_effort=high - < /tmp/prompt.txt > /tmp/review.txt 2>&1
```

- **`run_in_background: true` で投げる。** 5〜15 分かかるので、その間に自分の改修を進める
- 出力にはツール実行のログが混ざる。最終回答は `awk '/^codex$/{c++} c>=2'` で取り出す
- **`timeout` コマンドは macOS に無い**（`command not found`）。使わない
- Codex はリポジトリを読める。**読み取りだけと明言すれば、予約中のファイルでも競合しない**

### 何を聞くと効くか
「実測の症状」と「入れようとしている直し」を**両方**書いて、**穴を探させる**。
「これで合っていますか」ではなく「**見落としがちな穴を指摘してください**」と聞く。

### 実際に効いた指摘（2026-08-31）
1. **サイドバーの可視状態を取る公開 API は存在しない**（`sideBarVisible` は `when` 節専用）。
   だから「読んで分岐」ではなく「**結果を指定する冪等なコマンド**で揃える」— 入る `closeSidebar` /
   戻る `focusSideBar`。`openView` は QuickPick を出すコマンドなので誤り（**同梱の VS Code の
   ソースまで当たって確認していた**）
2. 走行中の押しを `pending = true` で溜めると、**3 連打で 1 回ぶん落ちる**。偶奇（反転）で持つ
3. 畳む幅と戻す幅を同じ値にすると、**境目で 1px ごとに点滅する**。デッドバンドを入れる

どれも自分では気づけていなかった。**Codex の指摘は、鵜呑みにせず自分で裏を取ってから反映する。**

## 8. 新しい敵対ケースを足す手順

1. 板に T 番号を起こし、触るファイルを予約する
2. `nimbus/docs/testing/adversarial.md` に節を足す（疑っている壊れかた / 期待する振る舞い /
   手順の要点 / **根拠にしたファイル:行**）。**根拠は実際に読んでから書く**
3. `nimbus/tests/gui/cases/adv-NN-<id>.mjs` を作る（4 節の掟を守る）
4. 固めて `--adversarial --only adv-NN` で走らせる。落ちたら 5 節で切り分ける
5. **直したら束を回し直す**（6 節・副次の判定に到達する）
6. 実装・仕様書・板を同じコミットで揃える

## 9. 移せる部分

**3・4・5・7 節（観点・掟・切り分け・Codex）は Nimbus に依存しない。** 他のプロジェクトで使うなら、
この 4 つをそのまま `~/.claude/skills/` へ写せばよい。

**6 節（効いた 4 つ）は、教訓は普遍だが実例が Nimbus 固有**（ケース 59・adv-10・`d02cd68fc1f`・
`nimbus/tests/gui/cases/`）。写すときは**見出しの 4 行だけを残し、実例は自分のプロジェクトのものに
差し替える** — 固有名詞のまま持っていくと、読んだ人に意味が取れない。

2 節と 8 節は Nimbus の道具（`run.mjs` の `--adversarial`）に依存するので写せない。
