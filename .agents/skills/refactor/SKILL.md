# リファクタリング

**振る舞いを変えないこと**が定義。振る舞いを変えたくなったら、それは別の作業として分ける
（同じコミットに混ぜると、壊れたときにどちらが原因か分からなくなる）。

## 始める前に（ここを飛ばさない）

```bash
git status --short          # 他のセッションが編集中のファイルを確認する
bash nimbus/scripts/test.sh # 今が緑であることを確かめる
```

- **他のセッションが編集中のファイルには触らない。** このリポジトリは複数の AI が同じブランチを
  同時に触る。整理したい対象が誰かの作業中なら、後回しにするか worktree を切る
- 緑でない状態から始めない。壊したのが自分か元からかを切り分けられなくなる
- 未コミットの自分の変更は先にコミットする（戻れる地点を作る）

## 何を整理するか

ドクターが機械的に見つけるもの:

```bash
node nimbus/scripts/doctor.mjs duplication orphans deps assets
```

- `duplication` — 同名 export / 6 行以上そっくりな実装 / 同じ文言の直書き
- `orphans` — どこからも import されていないモジュール
- `deps` `assets` — 使われていない依存・同梱ファイル

機械では分からないもの（読んで判断する）:

- **同じことを別の名前でしている 2 つの関数** — 名前が違うだけで役割が同じ
- **責務が混ざった関数** — 「取得して整形して保存する」のような、名前に and が入るもの
- **VS Code 依存が奥まで染みている** — 純粋ロジックが `vscode` を import しているせいで
  テストが書けない。`src/core/` へ切り出せば単体で検証できるようになる（Nimbus ではこれが最も効く）
- **名前が実態とズレている** — 実装が育って、名前が最初の意図のまま残っている

## やりかた

1. **1 コミット 1 種類。** 「重複の解消」と「命名の見直し」を混ぜない
2. **小さく動かす。** 抽出 → コンパイル → テスト、を 1 単位にする。まとめて動かして最後に通すのは避ける
3. **抽出先は使う側の近くに置く。** 共有したくなったら `src/core/`（VS Code 非依存）か
   `src/webview/`（Webview 共通）へ。むやみに `utils/` を作らない
4. **テストが無い場所を整理するなら、先にテストを書く**（`write-tests` スキル）。
   Nimbus のモジュールテストは VS Code を起動しないので、`src/core/` に切り出せた時点で書ける

## やりすぎない

- **2 回出てきただけでは共通化しない。** 3 回目で考える。早すぎる共通化は、後から
  「似ているが少しずつ違う」を無理やり 1 つにまとめた歪みとして残る
- **upstream（`src/vs/**`）は整理しない。** 追従できなくなる。触るのは
  `// --- Start Nimbus ---` の中だけで、それも最小限に
- **動いている UI をテスト無しで大きく動かさない。** GUI テストが未整備な部分は、
  先に `nimbus/tests/gui/cases/` にケースを足してから

## 終わったら

```bash
bash nimbus/scripts/test.sh        # モジュールテスト＋ドクター
bash nimbus/scripts/test.sh gui    # UI を触ったなら（ウィンドウが開くので断ってから）
```

- 振る舞いが変わっていないことを、テストとドクターの両方で確かめる
- 仕様書（`nimbus/docs/specs/`）の「設計」節に、置き場所が変わったことを反映する
- コアに触ったなら `nimbus/docs/core-changes.md` も直す
- コミットしたら push する（溜めると競合が解けなくなる）
